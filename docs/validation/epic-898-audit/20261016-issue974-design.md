# #974 대용량 SPARSE 볼륨 준비 설계

## 목적과 범위

Epic #898 / 통합 PR #1271의 기존 #892 desired state 및 #897 장기 작업 기반을 재사용한다. 신규 10TiB SPARSE XFS와 대용량 SPARSE ext4의 첫 포맷을 정상 서비스 API/UI 경로로 검증한다. THIN 실험은 현재 인수 증거로 사용하지 않는다. 별도 이슈·기능 브랜치·PR을 만들지 않고 최종 화면 표준 정리 #1275는 시작하지 않는다.

20초 probe와 크기별 format deadline 분리, 제한된 TERM/KILL 대기, FD9 writer 잠금 보존, SKIP_DISCARD 정책은 기존 구현을 재사용한다. 이번 변경은 그 위의 실제 프로세스 신원·완료 영수증·원작업 소유권·안전한 mount-only 재개 및 구조화된 진행 UI 계약을 완성한다.

## 신원과 완료 증거

포맷 전에 instance UUID / management operation UUID / revision의 originalFormatOwner와 볼륨 UUID, serial, 크기, formatter BOOT/PID/startTicks를 내구성 저널에 기록한다. 자식 프로세스 startTicks는 wait/reap 전에 수집한다. 같은 BOOT에서는 PID만으로 생존을 판정하지 않는다. PID/startTicks/argv가 불일치하거나 접근 권한·프로세스 관측이 불명확하면 inactive가 아니라 unknown으로 처리한다. BOOT가 달라지면 이전 숫자 PID를 재사용하지 않고 이전 BOOT의 프로세스 종료와 새 관측 BOOT를 구분한다.

formatterSuccessReceipt schema 2는 원작업, 볼륨·serial·크기, FS type/UUID, formatter BOOT/PID/startTicks, 고정 옵션과 discard 정책, exit 0 및 검증 시각을 묶는다. FS 헤더만 존재하거나 성공 영수증이 없는 부분 포맷은 자동 재포맷·마운트·RW probe를 수행하지 않는다. 기존 schema 1 영수증을 새로운 forward-resume 권한으로 승격하지 않는다.

## 재개와 동시성

정식 resume API는 동일 GlobalWriterLock 아래 유일한 RECOVERY_REQUIRED 원작업과 Native 저널/첨부 볼륨/활성 VM/ROOT/DATA/account/zone/현재 BOOT를 다시 확인한다. MGT에서 보존된 요구량과 동일 범위의 Native 논리 임대도 대조한다. 원래 논리 임대는 auxiliary operation이 취득·해제하지 않고 보존한다. checkpoint가 있으면 pending은 원작업에 정확히 속해야 하고, checkpoint가 없으면 pending 자체가 없어야 한다.

성공한 동일 FS에만 mount-only resume을 허용하며 Native resumeReceipt schema 1로 새 caller와 원작업의 연결, 같은 볼륨/FS/mount/BOOT, formatInvoked=false를 검증한다. 보조 작업은 COMPLETE_NO_CONFIG_CHANGE로 끝나고 원작업은 별도의 정상 reconcile 전까지 RECOVERY_REQUIRED를 유지한다. desired/native revision을 임의로 전진시키거나 Native configuration begin/commit을 실행하지 않는다. 활성 VM과 QGA transport는 검증하지만 이 API가 독립적인 guest DMI attestation을 추가했다고 주장하지 않는다.

기존 Native의 정상 MOUNT_EXISTING COMPLETE는 formatStarted가 없을 수 있다. 이 호환 경로는 strict inactive/termination false, 유효한 관리 mount/FS 기록과 포맷 관련 metadata 전무 조건으로만 허용한다. unknown 관측이나 부분 저널에는 적용하지 않는다.

## 포맷 정책과 보존

신규 포맷은 정확한 SPARSE/FAT 디스크 및 제공량, Native capability schema 2를 요구하고 SKIP_DISCARD의 검증된 고정 옵션을 사용한다. 완료된 동일 파일시스템의 mount-only 관찰에는 원래 DEFAULT/SKIP_DISCARD 기록을 그대로 대조한다. probe/format deadline 계산은 정수 overflow를 방지하고 상한 7200초를 유지한다.

기존 보호 partial 볼륨 021b0cac-327e-444b-9cff-3c9da0d1f539/VM51은 조회용 보존 대상이다. 포맷·repair·마운트·삭제·detach·재부팅하지 않는다. 원본 F1 Native143 및 기존 DATA는 수정하지 않는다. 실패한 새 부분 포맷도 자동 삭제하지 않으며 #895 데이터 보존 정책과 명시적 복구 경계를 유지한다.

## UI와 API

서버의 filesystemCompletionProven / resumeAllowed 두 strict boolean과 formatterObservationComplete 및 현재 identity를 사용한다. UI가 영수증 schema를 중복 해석해 서버 권한을 확장하지 않는다. 볼륨 이름/용량/FS, 단계/경과/기한/heartbeat, 현재 장치와 과거 장치 기록을 구분한다. 기본 화면은 조치 가능한 요약을 표시하고 raw 진단은 접는다.

표시 중인 진행 작업만 5초 간격으로 갱신하며, 종료·숨김·오류·unmount 시 멈춘다. instance/volume/caller/project/token/modal epoch가 바뀌면 오래된 응답을 버린다. 이미 받은 job ID는 GET으로만 추적한다. POST 결과를 모르면 자동 재전송하지 않고 RAM intent를 보존하며, 실패 job도 임의 재전송하지 않는다. 초기 생성의 createSharedFileSystem job과 첫 프로토콜 구성 job은 별개의 정상 단계를 유지한다.

## 배포와 실증 계획

정상 Maven 모듈 및 Checkstyle, 정상 UI unit/lint/production, Native 전체 대상 테스트를 exact commit에 고정한다. 관리 서버는 실제 배포 JAR의 관련 세 class family만 호환성 검증한 정상 빌드 산출물로 갱신한다. UI static 및 signed TEST runtime CODE는 각각 정식 배포/카탈로그 경로를 사용하며 template binary는 변경하지 않는다. DDL 변경과 새 공개 API command는 없다.

실증은 새 빈 초기 10TiB fixture에 signed CODE를 설치한 뒤 첫 서비스 설정을 실행한다. 새 볼륨의 API provisioning, 실제 qcow2 metadata allocation/no backing, guest serial/size/blank를 일치시킨다. XFS는 정확한 formatter만 25초 STOP/CONT하여 20초 초과를 검증하고 읽기 전용 API와 실제 Chrome UI 진행 상태를 함께 관찰한다. 이후 완료/응답 손실/재개/오류 차단 및 NFS·SMB I/O/재부팅 보존, ext4를 순차 검증한다.

13번 단일 GFS pool의 시작 scoped factor는 4이며 10TiB 정상 allocator 수용을 위해 일시 8을 적용했다. global factor/threshold는 변경하지 않는다. 테스트가 소유한 대용량 리소스 정리 후 시작값 4로 복원한다. GFS를 호스트 수만큼 합산하지 않는다. 물리 여유·증가량과 formatter AS를 관찰하고 보호 원본은 정리 대상에서 제외한다. 실증 결과와 한계는 별도 인수 기록에 실제 관측대로 기재한다.
