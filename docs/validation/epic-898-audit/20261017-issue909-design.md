## 적용 경계

구성 복원은 데이터 파일·블록 복원이 아니다. 업로드 ZIP을 격리 검증한 뒤 desired의 구조화 데이터만 현재 domain validator/renderer로 적용한다. runtime/rendered/system 파일을 직접 덮어쓰거나 private identity DB·설정 pin·비밀값을 수동 복원하지 않는다. archive 경로·entry 종류·압축/해제 크기·JSON 깊이·checksum/schema/version·비밀값 검사를 유지한다.

보존 DATA는 UUID/owner/domain/project/zone/pool/size 및 실제 장치/FS 신원으로 검증한다. 자동 대체·재포맷·삭제를 허용하지 않는다. 새 디스크는 SPARSE/FAT만 허용하고 정확한 VM/ROOT/DATA allocation provenance를 기록해 같은 자원만 재개한다. 전용 시험 자원은 정상 API로 정리하고 별도 API·호스트에서 부재를 확인한다. 기존 F1/ref59/ret61은 보호 대상이며 partial021b는 API/DB-only다.

비밀값은 archive/plan/artifact/로그/공개 증거에 저장하지 않는다. REQUIRES_REENTRY를 명시하고 적용 시점에만 입력한다. AD 보호 신원의 기존 선택 기능과 일반 비밀값 제외 백업을 구분한다. #909에서는 기존 AD 보호 신원과 서명 검증 경로를 재사용하며, 기존 템플릿의 유형·호환성 메타데이터나 신뢰 키를 임의로 변경하지 않는다.

## 확인된 최소 보완

- 중지·접근 불가 백업의 마지막 모니터링 관측과 STALE/UNAVAILABLE 구분을 확인·보완한다. 오래된 관측은 live 성공이나 LKG 승격 근거로 사용하지 않는다.
- CREATE_NEW와 다른 서비스 복원은 원본의 명시 listener 주소를 그대로 사용하지 않고 대상 PRIMARY 또는 승인한 IP로 매핑한다. PRIMARY는 실제 default NIC 또는 승인한 STATIC 계획의 정확한 주소로 해결한다. 빈 listenip은 API에서 wildcard이므로 필드를 지워 기본주소로 간주하지 않는다. 주소를 알 수 없는 DHCP 계획은 명시 PRIMARY를 차단하며 SELECTED listener 목록과 ACL은 보존한다.
- CREATE_NEW foundation 중단은 기록된 동일 artifact/VM/ROOT/DATA와 Native journal 신원을 검증한 기존 reconcile 경로로만 재개한다. 새 VM 추정·자동 재포맷은 하지 않는다.
- initial EXISTING DATA는 SYSTEM 템플릿 경로에서 VM/NIC/ROOT와 예약한 DATA를 먼저 기록·commit하고 ROOT-only 첫 부팅 후 정상 attach한다. private USER 템플릿의 기존 NEW-only 제한은 유지한다. 실제 파일시스템 관측 전의 XFS placeholder를 실제 FS 증거로 사용하지 않는다.
- 기존 DATA의 mount는 artifact에 기록된 FS UUID/type와 Native journal을 대조하고, mount 직전 장치 serial/size/path 및 blkid UUID/type를 다시 확인한다. 지원을 나타내는 정상 서명 manifest의 STORAGE_VOLUME_EXPECTED_FILESYSTEM_UUID_GUARD token과 fresh capability를 기존 DATA 복제의 자원 생성 전에 요구한다.
- initial EXISTING의 실제 검증에 호환 SYSTEM 이미지가 필요하면 검증된 정상 full-image 산출물만 재사용해 별도 시험 템플릿을 정상 등록한다. 새 Ready SYSTEM은 조회 순서상 잠시 기본 후보가 될 수 있으므로 원래 템플릿/기본값을 기록하고 명시 ID만 사용한다. 시험 소비자 정리 후 새 시험 템플릿만 삭제하며, 예상하지 않은 소비자가 있으면 삭제를 중단한다.
- 빈 NFS 활성화 실패로 원래 없던 network-endpoints.json만 남는 실제 rollback 결함을 같은 이슈에서 처리한다. 원래 요청 HMAC, 동결 SOURCE 및 DB 의미, 다른 여섯 파일, 정확한 기본 NIC와 NFS 런타임 부재를 검증한 명시 복구에서 기존 canonical restore만 사용한다. 이후 정상 replay/verify/rollback이 끝나야 완료로 판정하며 다른 프로토콜·DATA를 변경하거나 불명 상태를 부재로 간주하지 않는다.
- RESTORE_EXISTING에 기존 volume 외 resource의 명시 매핑을 연결한다. 매핑 변경 시 승인 token과 검토 확인을 초기화한다.
- dry-run의 current/desired/preserve 및 실제 필드 차이를 표시해 운영자가 적용 내용을 판단할 수 있게 한다.
- 비동기 known job을 scope와 함께 유지하고 조회 실패/유한 대기 후 같은 job 재조회로 이어간다. 불명 응답에서 mutation을 자동 재POST하지 않고 secret은 즉시 지운다.
- 적용 전 최종 승인·비동기 대화상자 종료·실패 결과 및 새로운 계획을 통한 명시 재시도를 구분한다. 전체 탭/대화상자 표준화는 시작하지 않는다.
- SystemVM 정상 재기동 후 NVMe 장치 이름이 달라지는 경우도 SOURCE 롤백을 검증한다. LOCAL 인증 복구가 성공한 뒤 canonical desired의 namespace runtime.backingPath 한 필드만 바뀌었다면, fresh configfs·장치 serial·UUID·크기와 현재 VM/소유/도메인/zone 및 SOURCE/PENDING/BOOT를 모두 대조한다. 그 검증을 통과한 경우에만 기존 generation restore로 동결 SOURCE의 선언 파일을 다시 정규화한 뒤 NFS 복구를 진행한다. 실제 커널 장치를 옛 경로로 바꾸거나 다른 구성 차이를 무시하지 않는다. 재진입과 관측 중 변경은 별도로 검증한다.
- 다른 화면/API에서 진행 중인 RUNNING 또는 RECOVERY_REQUIRED 작업도 정상 구성 복원 버튼과 계획 요청을 차단한다. 목록 조회 중 작업이 시작되는 경합도 다시 확인하며, 오류 상태에서 구성 백업·다운로드를 사용할 수 있는 경계는 유지한다.
