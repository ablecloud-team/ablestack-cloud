# #897 장시간 설정 변경의 사전 점검과 장애 격리 설계

#892의 snapshot·revision·원자적 롤백과 기존 인스턴스별 작업 큐를 재사용한다. 이 문서는 구현 및 실환경 인수를 위한 설계이며 완료 보고서가 아니다. 기존 Epic PR #1271에서 처리하며 새 이슈·브랜치·PR을 만들지 않는다.

| 요구 | 처리 원칙 | 인수 기준 |
| --- | --- | --- |
| 단일 writer | 인스턴스 async queue·지속 operation·writer lock·native scope/BOOT/세대 검증 재사용 | 같은 인스턴스의 두 요청이 동시에 효과를 적용하지 않음 |
| 작업량 및 자원 | source와 incoming 요청, 보수적 rendered 상한으로 예산을 동결하고 prepared target을 효과 전에 대조 | 메모리·staging·부하 부족, 불명확한 backing/서비스 관측에서 효과 전 차단 |
| 작업 생존 | 단계·진행률·heartbeat 영속화, 범위가 고정된 90초 논리 임대와 갱신·만료·해제 | DB 갱신0행/lease 갱신·해제 실패를 성공으로 표시하지 않음 |
| 취소·서비스 중단 | 안전 단계의 revision CAS 취소, 변경 시작 후 임의 중단 및 formatter kill 금지 | 취소1회·stale CAS·늦은 취소 거절, 원래 데이터 보존 |
| 유지보수 | 실제 graceful drain 미지원은 명시하고 기존 검토된 maintenance plan·이름·window·소유권 승인만 허용 | drain 지원을 위조하지 않으며 미승인 중단 요구를 차단 |
| 재시작·응답 불명 | 관리/게스트 재시작 뒤 기존 operation과 native journal·commit receipt 대조 | 같은 작업의 완료 정리·롤백·수동 복구, 효과 중복0 |
| UI | 작업 탭의 phase·progress·heartbeat와 읽기 전용 자동 갱신, 안전 제어 및 영향 안내 | 실제 브라우저의 동작·조회 실패·동일 작업 재추적·terminal 갱신 중지 |

논리 임대는 RAM이나 디스크의 물리적 선점을 뜻하지 않는다. native4항목 요구량(minimumMemoryAvailableBytes, stagingRequiredBytes, maxLoadPerCpu, requireSessionDrain)은 같은 작업에서 변경하지 않는다. 효과 전 prepared target이 동결한 상한을 넘으면 차단하고 기존 복원 경로를 사용한다. rendered 실제 관측값과 추정 상한을 구분하며 미관측 값을 관측 완료로 바꾸지 않는다.

운영자가 설정할 최소 메모리 여유 storage.service.operation.minimum.memory.available.mb는 기본256MiB, 동적 상향 하한으로 설계한다(256..1,048,576MiB). 작업 시작 시 추정치와 이 값 중 큰 값으로 동결하며 설정 변경은 이후 작업에만 적용한다. 실환경 부족 시험은 전용 서비스에16GiB 하한을 요구하여 수행하고 실제 OOM을 유발하지 않는다.

새 typed 사전 점검은 호환 native와 명시적으로 활성화한 서비스의 control에 연결한다. 기존 비활성 서비스는 빈 payload의 legacy 사전 점검을 유지한다. 새 서비스는 서명 CODE 적용 → control 비활성 상태의 최초 NFS/generation 생성 → IN_SYNC 및 scope 확인을 거친 정식 opt-in 순서를 사용한다. 빈 generation에 새 임대 권한을 주는 예외를 추가하지 않는다.

DB 단계 저장 실패와 native commit 이후 저장 실패는 구별한다. 이미 native target commit이 확인된 경우 SOURCE를 무턱대고 덮어쓰지 않고 기존 commit receipt 및 forward finalization 경계를 보존한다. heartbeat 저장 실패는 다음 효과·승격을 보류하되 기존 안전 롤백 경로를 막지 않는다.

일반 BACKUP은 기존 관리측 전용 계약을 유지한다. includeRuntime=false, Stopped/Error 서비스의 desired ZIP 수집에는 실행 중인 guest나 guest 임대를 강제하지 않는다. 명시적으로 opt-in한 Running 서비스에서 runtime 관측을 포함하는 백업만 같은 writer·heartbeat·사전 점검·논리 임대를 사용한다. 이 읽기 전용 작업은 COMPLETE_NO_CONFIG_CHANGE로 끝나며 desired/native revision을 증가시키지 않는다. 재시작 뒤 보호된 artifact·SOURCE·VM/DATA/BOOT 증거가 확정되어야 동일 결과를 반환하고, 수집 결과가 확정되지 않았다면 BLOCKED로 기록한다.

lease 종료는 성공뿐 아니라 실패·취소·롤백에도 적용한다. 실제 임대를 얻은 작업은 완료 상태를 기록하기 전에 정리 의도와 SOURCE 또는 TARGET 증거를 보존한다. Native release의 최소 ACK를 관측 결과로 오인하지 않고 fresh status로 정확한 범위의 부재를 확인한다. 해제 응답 유실·DB0행·foreign scope는 cleanupPending/RECOVERY_REQUIRED로 보존하며, 재시작 뒤 같은 작업에서 증거를 재확인해 정리한다. 확정된 TARGET에는 SOURCE 변경을 재실행하지 않는다.

기존 cloud.storage_service_operation, cloud.storage_service_operation_control 및 storage_service_instance.operation_control_policy_json을 사용한다. control의 policy_json·lease_json과 instance 정책은 LONGTEXT다. 이번 변경은 새 테이블·컬럼을 요구하지 않는다. 13번의 실제 메타데이터에서 control12컬럼·3인덱스와 instance 정책 LONGTEXT, europa-4.23-sharedfs-operation-control-v1 및 europa-4.23-sharedfs-operation-control-policy-v1의 Complete를 읽기 전용으로 확인했다. 새 운영 하한은 configuration 항목이다.

격리 시험 서비스 issue897-isolation-20261016의 새 ROOT와 DATA는 실제 SPARSE/no backing으로 확인한다. 기존 서비스와 보호된 원본10TiB021b는 시험 포맷·repair·mount 대상에서 제외한다. 재부팅·QGA 단절·취소 시험은 이 격리 서비스에서 수행하고 각 job·operation·revision·scope·복구 결과를 기록한다. API 검증과 실제 UI 검증을 분리하고 mock/unit PASS를 실환경 PASS로 대신하지 않는다.

#1275 최종 UI 표준화는 이 작업에 포함하지 않는다. 작업 탭의 기능 필드와 기존 제어 컴포넌트만 보완한다. 구현·정상 모듈 빌드·13번 배포·API·실제 UI 인수·Epic PR 반영 후 완료 댓글을 기록하고 #897을 닫은 뒤 다음 이슈를 보고하고 대기한다.
