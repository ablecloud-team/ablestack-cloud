# #914 다수 NFS Export 부팅 reconcile 설계

L2 네트워크 준비는 #913의 단일 MAC 기반 경로를 유지한다. 본 작업은 부팅 시 프로토콜 준비·상세 검증·기한·상태를 일치시키며 기존 API·관리 서버 DB 스키마는 재사용한다.

## 기존 구현과 개선 범위

기존 legacy BOOT/desired SHA 체크포인트, native generation/current/pending 보호, exact PID 소유권과 FD9/pidfd 기반 유한 종료를 유지한다. 단순 systemd timeout 증가는 완료로 보지 않는다.

공통 coordinator는 활성 export/endpoint/mode 작업 수를 실제 순차 probe 동시성 1 기준으로 산정한다. 내부 예산은 600~1,500초로 제한하고 systemd의 기존 1,800초 상한보다 먼저 종료한다. BOOT/desired hash/immutable pointer가 바뀌면 이전 완료 기록을 재사용하지 않는다. 성공한 프로토콜만 건너뛰며 NFS 실패가 SMB 재적용을 유발하지 않게 한다.

NFS는 exact-owned process/listener·runtime export inventory·rpc 등록을 확인한 뒤 endpoint/mode별 대표 probe와 나머지 상세 검증을 수행한다. 실제 성공은 자식 종료·unmount·mountinfo·임시 디렉터리 제거가 확인된 경우만 기록한다. 권한에 따른 skip은 별도 이유와 수로 공개하며 ACL을 확대하지 않는다. 미확정 자식이나 cleanup 잔존은 복구 필요 상태를 유지한다.

health.bootReconcile schema1은 현재 BOOT·desired hash와 상태(RECONCILING/READY/DEGRADED/FAILED/HELD), phase/attempt/elapsed/deadline/remaining/heartbeat, 프로토콜별 listener 준비·probe 수·검증 완료와 구조화된 마지막 실패를 제공한다. listener 준비를 전체 검증 완료로 승격하지 않는다. monitor는 부팅 작업과 독립적으로 관측하되 boot 진행 중 endpoint writer를 실행하지 않는다. UI는 기존 작업 탭의 읽기 전용 기능으로만 연결하며 #1275 레이아웃 정리는 시작하지 않는다.

## 기존 VM 배포와 적용 대기 선언

정상 서명 CODE 번들은 기존의 standalone entrypoint3개를 유지한다. 신규 공통 Python 모듈은 entrypoint 안의 동일 원문으로 포함하여 새 외부 라이브러리 설치를 요구하지 않는다. 기존 unit이 monitor를 reconcile 뒤로 순서 지어도 coordinator가 현재 BOOT의 최소 공개 진행 cache를 원자 게시한다. 예전 runtime/port 관측을 새 시각의 정상 상태로 재포장하지 않는다. 새 템플릿의 monitor는 네트워크 준비 뒤 독립 관측한다. 전체 boot transaction은 기존 보호 writer lock FD9를 사용하며 미확정 자식이 보유한 lock을 강제로 해제하지 않는다.

다수 Export의 초기 정책을 준비하는 정상 deferapply 경로에서 Allocated 선언이 실제 실행 중인 Ready와 혼동되는 기존 검증을 확인했다. Allocated 선언은 정확한 backing 신원·native TARGET·동일 작업 snapshot 보호를 유지하고, 명시적으로 완전한 NFS 관측에서 해당 pseudo가 노출되지 않았을 때만 미적용 상태로 검증한다. listener 오류·관측 불가·부분 파싱이나 이미 노출된 선언은 거절한다. Ready를 부여하거나 원작업을 새 작업으로 대체하지 않으며 정상 same-operation forward finalization 경로를 유지한다.

## 전용 검증 자원의 적용 대기 NFS 복구 보완

기존 control-off writer가 커밋 전 TARGET witness를 저장하지 않아, 미노출 NFS의 정상 복구도 중단되는 경로를 실제 신규 SPARSE 테스트 자원에서 확인했다. 이후 모든 Native writer는 선택적 operation control과 관계없이 durable target witness → verify → commit 순서를 지킨다. 저장 실패 시 commit하지 않는다. rendered commit 소유권은 유지한다.

이미 witness 세 필드가 모두 누락된 경우 일반 requireTarget은 그대로 거절한다. 보호된 NEW private USER fixture 생성 permit/claim/receipt, 최초 단일 Allocated NFS 선언, 정확한 six-table TARGET/응답, VM 및 ROOT1/DATA1 전체 할당 tuple, 커밋 전 schema2 formatter receipt와 현재 물리 serial/FSUUID/BOOT, writer·formatter·logical lease 유휴를 매번 확인하는 제한 경로만 별도 late recovery authority를 저장한다. 누락된 과거 witness를 채우거나 기존 데이터/부분 formatter receipt로 이 경로를 확대하지 않는다.

생성 receipt에는 과거 guest BOOT/DMI/deviceId가 없다. 해당 기록이 있었다고 주장하지 않으며, 동일 BOOT의 precommit formatter receipt와 보호된 신규 단일 DATA 할당 및 현재 VM transport를 조합한 별도 권위로 한정한다. 실제 전체 데이터 hash 검증으로 표현하지 않는다.

Java11 직접 관련 5 suites/86 tests는 정상 Maven 빌드 및 실제 복구 인수와 구분한다. 실제 Runtime factory의 control-off RED → GREEN 순서 회귀, 실제 보호 생성 receipt와 DTO, partial/foreign ROOT·DATA·BOOT·lease·late snapshot drift 거절을 포함한다. 정상 배포는 Manager outer/anonymous family의 실제 바이트 차이와 새 validator만 비교하여 반영하며, 직접 javac 산출물을 사용하지 않는다.

## 100개 Export 구성 중 확인한 QGA 인자 길이 한계

실제 13번째 Export ACL 적용에서 QGA가 /bin/bash 실행 인자 길이 초과로 실패했다. 기존 NFS apply는 unmasked JSON을 base64로 변환해 단일 shell 인자에 포함했다. Export별 검사·디렉터리 생성 증거가 누적되므로 작은 구성에서 통과한 경로가 다수 Export에서 중단됐다. 실패 원작업은 rev42 RECOVERY_REQUIRED, Native는 current41 및 같은 op42 PREPARED 상태였으며 canary8은 재부팅 기준선과 동일했다.

UTF-8 payload가 32KiB를 초과하는 일반 Native 명령은 기존 anonymous memfd 및 32KiB 분할 전송 경로를 사용한다. 일반 Native stdin reader의 기존 8MiB 상한을 QGA 호출 전에 확인하며, 작은 요청·정적 네트워크 설치·기존 보호 payload의 의미는 유지한다. 설정 JSON을 줄이거나 검사 증거를 버리지 않고 같은 바이트를 전달한다. Payload를 인자로 되돌리거나 디스크 파일로 대체하는 우회, 불확정 commit의 재전송은 허용하지 않는다.

회귀는 13개 Export 크기의 인자 초과 재현, 전송 바이트 동일성, UTF-8 byte 경계, QGA 전 8MiB 거절, close-before-commit, 불확정 commit 1회 및 capability 미지원 시 중단을 포함한다. 이 변경은 KVM Wrapper에 국한되므로 정상 KVM 모듈을 다시 빌드하고 호스트의 해당 클래스만 교체한다. Native CODE3·SystemVM 이미지·관리 서버 및 DB 스키마 변경은 필요하지 않다.

원작업은 정상 reconcile의 exact SOURCE 복원 경로로 정리한다. ROLLED_BACK·기존 current41·pending 부재·ACL 부재·기존 데이터 보존을 확인하기 전에는 ACL 요청을 다시 제출하지 않는다. 정리 후 같은 Allocated Export에 새 명시적 ACL 요청을 적용하며 Export 재생성·DATA 재포맷은 하지 않는다.

## 실제 확대 검증에서 확인한 BEGIN 경합과 NFS 실패 관측

새 dual VM의 4번째 ACL 작업은 Native generation 시작 전에 BLOCKED됐다. 같은 관리 서버 ctx/job/agent sequence에서 generation begin 요청 뒤 STORAGE_WRITER_BUSY와 종료코드75, 같은 원작업의 BLOCKED를 확인했다. 현재 Native8은 보호된 VERIFIED8 선언과 일치하고 pending도 없었다. 실제 락 소유자는 과거 로그로 입증하지 못했다. monitor의 주기적 network endpoints reconcile이 같은 FD9 락을 잡는 구체적 경쟁 경로는 소스에서 확인했다.

Manager의 generation begin에 한해 정확한 본문 실행 전 BUSY 응답을 최대4회·전체30초 한도에서 처리한다. 같은 thread writer/instance/VM/operation/revision/phase/state/이전snapshot을 고정하고, 신선한 writer-idle 및 명시적 pending null·취소 상태를 확인한 뒤 같은 요청을 보낸다. 다른 action·일반 오류·형식 오류·전송 결과 불명에는 재전송하지 않는다.

기존 VM의 15번째 ACL은 런타임 apply 실패 후 정상 ROLLED_BACK으로 끝났다. Native45 IN_SYNC, pending/lease 부재, 기존 파일8개·두 포맷 영수증·14개 Ready와 15번째 Allocated/ACL 부재를 확인했다. 과거 Target 실패 JSON은 회수하지 못했으므로 timeout·권한 실패 등으로 원인을 추정하지 않는다.

Native는 lastFailure와 readiness 정보를 출력하지만 기존 host failure composer는 top-level message/errorCode만 사용해 세부를 No guest diagnostic으로 소실할 수 있었다. NFS apply의 기존 상세가 비어 있고 민감 payload가 아닌 경우에만, 알려진 protocol/phase/code·UUID·IPv4·port·boolean·정리 상태·probe count를 엄격 검증해 진단 문자열로 전달한다. 비밀·임의 본문·exportName을 출력하지 않고 기존 마스킹·stdout 원형·재시도 의미를 유지한다. 이후 검증에서는 명확히 롤백된 Source에서 새 ACL 요청을 적용하고 실제 결과를 관측한다.


## 15개 CLIENT 초기화와 listener 고정 대기 보완

최신 관리 서버·호스트 수정 후에도 같은 15번째 ACL이 정상 ROLLED_BACK으로 끝났다. 목표 Ganesha PID는 15개 CLIENT를 순서대로 초기화한 뒤 시작 15초 후 SERVER INITIALIZED에 도달한 같은 초에 종료됐다. Source 복원 PID는 14개 CLIENT 초기화 후 유지됐다. 양쪽에서 공통으로 출력된 keytab 경고를 원인으로 분류하지 않는다. 실패 Target stdout은 회수하지 못했으며, 관리 서버·호스트의 작업 맥락과 별도의 Ganesha init/stop 시각, 실제 production 함수의 고정 15초 경계를 대조했다.

Listener gate는 기존 protected configuration 및 정확한 PID/startTicks snapshot을 사용한다. 기존 Ganesha parser가 산출하는 CLIENT principal 수를 기준으로 기본 15초에 principal당 2초를 더하되, 호출자의 기존 전체 기한에서 정리 시간 5초를 뺀 시점을 넘지 않는다. 여러 principal을 가진 CLIENT도 보수적으로 계산하며, 전체 명령 기한을 새로 시작하거나 확대하지 않는다. 준비 중인 정상 initializer를 반복 재시작하지 않는다.

연결 시도와 sleep은 이 지역 기한을 넘지 않게 제한하고 listener 준비 후 PID/startTicks/configuration/BOOT snapshot을 다시 대조한다. 죽거나 교체된 PID와 다른 프로세스가 연 포트를 성공으로 처리하지 않는다. 실제 Native가 생산하는 ENDPOINT_LISTENER_NOT_READY 및 EXPORT_BINDING_MISMATCH도 기존의 엄격한 비밀 비포함 NFS 진단 목록에 포함한다.

회귀는 실제 start_ganesha_endpoints 함수와 실제 config serializer/parser를 연결하여 15 CLIENT의 16초 준비, 100 CLIENT의 101초 준비, 단일 Export의 복수 CLIENT, dual·복수 endpoint, 전체 기한의 정리 여유, PID 종료/교체 및 불완전 config 거절을 확인한다. 보호된 실제 파일·프로세스 관측은 기존 별도 회귀가 담당하며 fake clock 결과를 실클러스터 인수로 표현하지 않는다.

## 최신 upstream 통합

2026-10-17 upstream 기본 브랜치 dc31262567f2afe5f6278fae61c1cef7e307fe3e를 로컬 ablestack-europa에 먼저 fast-forward한 뒤 Epic 브랜치 567개 커밋을 재배치했다. local/origin/upstream 기본 브랜치 차이는 모두 0/0이다. 독립 번역 키 충돌만 해결했으며 최종 사전 의미는 이전 Epic·이전 base·새 upstream의 3방향 병합과 정확히 일치한다. upstream에 이미 있던 중복 번역 키는 별도 정리하지 않았다.

보관한 진행 중 수정 파일들은 재배치 후 바이트 단위로 일치한다. 이전 Epic과의 변경 경로 9,184개는 새 upstream의 변경 경로와 같고 그 밖의 경로 차이는 없다. 공통 UI 변경이 포함되므로 이전 UI 전체 빌드의 Source pin을 새 HEAD의 전체 빌드로 대신 주장하지 않고, 새 UI 모듈을 빌드·배포하여 SharedFS API·실제 Chrome 검증을 다시 수행한다. 관리 서버의 SharedFS 소스가 동일한 경우에는 실제 배포된 최소 클래스와 새 Source의 관계를 별도로 검증한다.


## 23번째 ACL 커밋 경합과 동일 요청의 검증된 TARGET 완료

Listener 수정 후 22개 Export가 Ready가 됐고 23번째 Export의 Ganesha도 CLIENT 초기화와 listener 준비를 정상적으로 끝냈다. 그 뒤 동일 관리 서버 실행 문맥과 agent sequence에서 generation verify 성공 다음 commit이 본문 진입 전 STORAGE_WRITER_BUSY / exit 75로 거절됐다. 이 결과는 전송 결과를 알 수 없는 timeout과 구분한다. 잠금 보유자는 과거 로그로 특정하지 않았다.

BEGIN의 기존 제한적 처리를 verify·commit·finish에도 적용한다. 정확한 두 필드의 BUSY 결과에서만 전체 30초·최대 4회 한도로 동일 요청을 진행하며, instance/VM/operation/revision/phase/state/이전 snapshot과 thread writer를 고정한다. 신선한 writer-idle, 같은 Native SOURCE 또는 커밋된 TARGET, pending 소유권과 취소 상태를 확인한다. finish가 이전 COMPLETE 작업을 정리하는 경우에는 같은 instance의 더 높은 revision을 가진 새 active parent writer까지 별도로 고정한다. 일반 실패·형식 오류·알 수 없는 전송 결과나 원래 ACL 생성 요청에는 이 처리를 적용하지 않는다.

실제 실패 작업은 DB가 SOURCE68로 복원된 뒤 Native VERIFIED69와 실행 중 TARGET 구성이 남았다. SOURCE의 23번째 선언은 Allocated이고 ACL은 없으며 TARGET은 그 선언을 Ready로 바꾸고 CIDR ACL 한 행을 추가한 구성이다. Native PREPARED 전용의 일반 NFS grant는 VERIFIED 상태의 SOURCE replay를 거절하므로, 임의 phase 변경이나 pending 삭제로 우회하지 않는다.

같은 원래 관리자 계정의 명시적 정상 reconcile 요청에서만 검증된 NFS ACL TARGET을 완료하는 별도 조건을 둔다. background recovery에는 이 권위를 부여하지 않는다. 대상은 원래 NFS ACL 생성 작업에 한정하며 취소·다른 active writer·후속 성공 revision·ROOT/rendered/identity 유지보수 등 다른 권위를 빌리지 않는다. 아래 조건을 모두 만족해야 한다.

- durable response·TARGET snapshot·VM/ROOT/DATA binding·원래 BOOT·구성 checksum witness가 보존되어야 한다.
- Native의 보호된 frozen SOURCE와 frozen VERIFIED TARGET, 실제 canonical 7개 파일, 이전 current와 같은 작업 pending이 정확히 일치해야 한다.
- DB는 원래 SOURCE 또는 원래 TARGET과 정확히 같아야 한다. 허용되는 차이는 한 NFS Export의 Allocated→Ready와 그 Export의 CIDR/IP ACL 한 행뿐이며, 기존 ACL·나머지 Export·다른 네 테이블·신원/비밀 설정은 변경할 수 없다.
- 신선한 유휴·물리 DATA/formatter·실제 runtime 검증과 취소 검사를 거치고, 정상 desired-state snapshot 복원과 generation verify→commit을 사용한다. 기존 committed-TARGET finalization 조건은 완화하지 않는다.

변경 의도를 DB 복원 전에 남기고 복원 뒤에는 TARGET 상태에서 같은 작업으로 재검증할 수 있게 하여, 중간 중단이 새 ACL 요청 재전송으로 이어지지 않게 한다. 불완전한 증거·다른 BOOT/VM/DATA·구성 변경은 복구 필요 상태를 유지한다. 이 경로는 누락된 과거 witness를 생성하거나 Native 상태·DATA·DB를 운영 도구로 직접 교정하는 기능이 아니다.

관리 서버의 정상 모듈 빌드 산출물에서 변경 클래스와 새 검증 helper만 배포한다. Native CODE·System VM 이미지의 소스는 변경하지 않으며 각 구성 요소의 빌드 기준을 별도로 기록한다. 기존 복구 대화상자의 기능 안내는 검증된 원래 TARGET 완료와 보존된 SOURCE 복원 두 결과를 정확히 설명하도록 조정한다. #1275의 레이아웃 정리는 시작하지 않는다. 실제 정상 복구·100개 확장·냉부팅 결과는 인수 보고서에서 별도로 확정한다.


재검증 명령이 갱신하는 TARGET verifiedAt은 유효한 양수 시각인지 계속 확인하되 동일 구성의 안정된 TARGET 권위 지문에서는 제외한다. SOURCE의 전체 current와 verifiedAt은 그대로 고정한다. 따라서 DB TARGET 복원 뒤 또는 Native 재검증 직후 중단돼도 같은 scope·BOOT·구성·원래 요청의 정상 재개를 허용하고, 실제 SOURCE·구성 checksum·리비전 변경은 거절한다.

중앙 BEGIN은 최초 명령 전에 읽기 전용 관측으로 BOOT/current/구성 checksum/전체 7개 파일을 RAM에 고정한다. durable checkpoint를 BEGIN 뒤에 저장하는 기존 호출 경로도 유지하며, SOURCE 관측이 불명확하거나 달라지면 BUSY 뒤 재발행을 하지 않는다. 최초 조회부터 동일한 30초 예산을 차감한다. 이 경로의 Native 성공 플래그와 실시간 health 성공 플래그는 JSON boolean만 허용한다.

실제 보존된 작업의 읽기 전용 검증에서 ACL snapshot은 정식 schema-Diplo-After.sql의 13개 컬럼을 포함함을 확인했다. VO가 노출하는 11개 필드만으로 구성한 테스트 전제를 바로잡고 updated·removed의 SQL TIMESTAMP 형식을 정확히 확인한다. 신규 ACL의 removed는 null이어야 하며 updated는 null 또는 양의 정수 시각이어야 한다. created와 updated 사이에 스키마가 보장하지 않는 순서 조건은 추정하지 않는다. 허구의 11컬럼 호환 경로나 임의 컬럼은 허용하지 않으며 다른 delta·Native·원래 요청 권위 조건은 유지한다. DB DDL이나 실제 작업 상태의 수동 수정은 없다.


## COMPLETE 이후 Native 정리 경합의 동일 writer 처리

Dual 확대의 42번째 ACL은 API 작업 COMPLETE88과 Native current88 커밋을 성공했지만 같은 작업의 COMMITTED pending이 남았다. 해당 관리 서버 실행 문맥·agent sequence에서 finish 명령의 본문 진입 전 STORAGE_WRITER_BUSY/exit75와 후속 pending 경고를 대조했다. DATA·포맷 영수증·파일·장치 신원은 동일했다. 기존 finished 콜백은 COMPLETE 전환 뒤 Native finish를 best effort로 실행하므로 커밋 성공과 정리 완료를 구분한다.

같은 콜백의 TLS writer가 유지되고 phase/state가 모두 COMPLETE인 finish만 제한된 BUSY 재시도에 추가한다. 같은 instance/VM/op/revision/previous snapshot, 실제 committed TARGET·BOOT와 취소 검사를 그대로 고정하며 전체30초/최대4회와 불명확 결과 재전송 금지도 유지한다. 다른 terminal 상태·다른 action·owner/phase 변경은 허용하지 않는다.

다음 정상 writer의 기존 preflight는 이전 COMPLETE pending을 새 active parent의 권위로 정리한 뒤 mutation을 시작한다. 확대 시험은 이 정상 경로를 재사용하며 운영 도구가 Native pending을 직접 삭제하지 않는다. API Ready/commit 및 exact COMMITTED pending을 정리 완료 IN_SYNC와 혼동하지 않고, 최종 냉부팅 전에는 반드시 pending 부재와 IN_SYNC를 별도로 확인한다.


## ENOSPC 이전 checkpointless 선언의 검증된 SOURCE 확인

확대 중 관리 서버의 MySQL 임시 공간 부족으로 Main의 다음 NFS 선언이 실패했다. 해당 원작업은 RECOVERY_REQUIRED이며 Export 행과 실제 share 경로가 없고, 직전 COMPLETE143의 Native current·canonical 구성·두 포맷 영수증·기존 파일은 보존됐다. 원작업의 이전 schema2 snapshot은 보존됐지만 Native/local/rendered checkpoint와 TARGET snapshot·witness는 만들어지지 않았다. 일반 interrupted 복구가 SOURCE protocol을 재적용하려다 generation scope 검증에서 거절된 결과도 보존한다.

읽기 전용 JVM 검증에서는 원작업의 이전 snapshot, 직전 COMPLETE의 TARGET snapshot, 현재 여섯 DB 테이블이 숫자·문자열·boolean을 구분한 타입까지 정확히 같았다. 직전 COMPLETE의 정상 TARGET BOOT/binding/config witness와 현재 ROOT·두 DATA binding도 일치했다. 이 관측은 복구 실행 또는 누락된 과거 checkpoint 생성으로 표현하지 않는다.

별도 경로는 같은 원래 관리자의 명시적 ORIGINAL reconcile에 한해 checkpointless NFS Export 생성의 현재 SOURCE를 확인한다. 기존 정상 SOURCE/TARGET 복구 조건은 완화하지 않는다.

- 원래 RC 작업과 원래 요청 fingerprint를 고정한다. Native/local/rendered/TARGET 권위가 실제로 없고, schema2 이전 snapshot이 직전의 유일한 하위 COMPLETE TARGET 및 현재 DB와 엄격하게 일치해야 한다.
- 직전 COMPLETE의 기존 response 객체와 정상 BOOT/VM/ROOT/DATA/config witness를 SOURCE 권위로만 읽는다. 더 높은 verified revision·다른 unresolved writer·취소·불완전한 control/upgrade 관측은 거절한다.
- 현재 Native IN_SYNC·pending 부재·보호된 frozen SOURCE/current/전체 canonical 의미·BOOT 및 모든 파일 DATA의 실제 formatter/장치/파일시스템 신원을 검증한다. 신선한 writer-idle와 명시적 lease 부재도 확인한다.
- 정상 operation verify/observe를 이용한 runtime 확인과 DB/Native/binding/physical 재관측을 finalization 전후 경계에서 반복한다. 정상 검증의 임시 probe와 정리는 허용하되 protocol replay·config-generation 변경·실제 DATA 쓰기를 추가하지 않는다.
- 별도의 unchanged-SOURCE 의도를 보존한 뒤 원작업만 ROLLED_BACK으로 끝내고 원래 실패 진단과 SOURCE 확인 결과를 함께 남긴다. 직전 COMPLETE, 원래 snapshot 및 과거 checkpoint는 변경하지 않는다.
- 새로운 의도가 남은 상태에서 background 또는 다른 actor가 generic SOURCE replay로 빠지지 못하게 막는다. eligible 후보의 증거 누락·drift도 기존 apply 경로로 fallback하지 않는다.

직접 Java11 회귀는 기존 Manager에서 DB SOURCE restore/replay 시도를 감지하는 RED와 새 경로의 통합 GREEN을 구분한다. 실제 정상 빌드 helper를 이용한 SOURCE143 RAM-only qualification에서 response 객체·실제 Native status/frozen·두 DATA binding까지 확인한 뒤 배포와 실제 ORIGINAL 복구를 별도로 승인한다. 아직 실행하지 않은 복구나 100개 냉부팅 인수는 이 설계 변경으로 완료 처리하지 않는다.
