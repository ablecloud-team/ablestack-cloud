# #914 다수 NFS Export 부팅 reconcile 설계

L2 네트워크 준비는 #913의 단일 MAC 기반 경로를 유지한다. 본 작업은 부팅 시 프로토콜 준비·상세 검증·기한·상태를 일치시키며 기존 API·관리 서버 DB 스키마는 재사용한다.

## 기존 구현과 개선 범위

기존 legacy BOOT/desired SHA 체크포인트, native generation/current/pending 보호, exact PID 소유권과 FD9/pidfd 기반 유한 종료를 유지한다. 단순 systemd timeout 증가는 완료로 보지 않는다.

공통 coordinator는 활성 export/endpoint/mode 작업 수를 실제 순차 probe 동시성 1 기준으로 산정한다. 내부 예산은 600~1,500초로 제한하고 systemd의 기존 1,800초 상한보다 먼저 종료한다. BOOT/desired hash/immutable pointer가 바뀌면 이전 완료 기록을 재사용하지 않는다. 성공한 프로토콜만 건너뛰며 NFS 실패가 SMB 재적용을 유발하지 않게 한다.

NFS는 exact-owned process/listener·runtime export inventory·rpc 등록을 확인한 뒤 endpoint/mode별 대표 probe와 나머지 상세 검증을 수행한다. 실제 성공은 자식 종료·unmount·mountinfo·임시 디렉터리 제거가 확인된 경우만 기록한다. 권한에 따른 skip은 별도 이유와 수로 공개하며 ACL을 확대하지 않는다. 미확정 자식이나 cleanup 잔존은 복구 필요 상태를 유지한다.

health.bootReconcile schema1은 현재 BOOT·desired hash와 상태(RECONCILING/READY/DEGRADED/FAILED/HELD), phase/attempt/elapsed/deadline/remaining/heartbeat, 프로토콜별 listener 준비·probe 수·검증 완료와 구조화된 마지막 실패를 제공한다. listener 준비를 전체 검증 완료로 승격하지 않는다. monitor는 부팅 작업과 독립적으로 관측하되 boot 진행 중 endpoint writer를 실행하지 않는다. UI는 기존 작업 탭의 읽기 전용 기능으로만 연결하며 #1275 레이아웃 정리는 시작하지 않는다.

## 인수 게이트

| 범위 | 게이트 |
|---|---|
| 기한·상태 | 1/10/100 × v4/dual × 단일/복수 endpoint의 기한 산정·상한, heartbeat, pending/held/unknown의 완료 오판 방지 |
| 독립 재시도 | NFS 첫 실패 뒤 성공 시 SMB1회, BOOT/hash/PID 변경 무효화, rendered/legacy 동일 계약 |
| probe | cold readiness 지연, 특정 export timeout/permission, 실제 자식 hang 종료·cleanup 및 미확정 D-state 회귀 |
| 실환경 | 소유한 SPARSE 시험 VM에서 1/10/100 Export 냉부팅과 외부 파일 I/O, 단일/복수 endpoint·port, NFS/SMB 복구 |
| 관측 | 진행 중 runtime-ready/probe-pending과 최종 API·실제 Chrome 상태 일치, QGA/관리 서버 접속 단절 중 guest 독립 완료 |
| 보존·마감 | 보호 원본 RO 대조, 소유 자원 정상 API 정리, 모듈/이미지 빌드·배포·증거·Epic PR 반영 후 완료 댓글과 종료 |

새 이슈·개발 브랜치·PR을 만들지 않는다. 모든 새 디스크는 SPARSE/FAT만 허용하며 기존 보호 partial에는 직접 guest 작업·format/repair/mount/detach/delete/reboot를 하지 않는다. 실제 실행별 결과와 제한은 완료 보고서에서 구분한다.

## 기존 VM 배포와 적용 대기 선언

정상 서명 CODE 번들은 기존의 standalone entrypoint3개를 유지한다. 신규 공통 Python 모듈은 entrypoint 안의 동일 원문으로 포함하여 새 외부 라이브러리 설치를 요구하지 않는다. 기존 unit이 monitor를 reconcile 뒤로 순서 지어도 coordinator가 현재 BOOT의 최소 공개 진행 cache를 원자 게시한다. 예전 runtime/port 관측을 새 시각의 정상 상태로 재포장하지 않는다. 새 템플릿의 monitor는 네트워크 준비 뒤 독립 관측한다. 전체 boot transaction은 기존 보호 writer lock FD9를 사용하며 미확정 자식이 보유한 lock을 강제로 해제하지 않는다.

다수 Export의 초기 정책을 준비하는 정상 deferapply 경로에서 Allocated 선언이 실제 실행 중인 Ready와 혼동되는 기존 검증을 확인했다. Allocated 선언은 정확한 backing 신원·native TARGET·동일 작업 snapshot 보호를 유지하고, 명시적으로 완전한 NFS 관측에서 해당 pseudo가 노출되지 않았을 때만 미적용 상태로 검증한다. listener 오류·관측 불가·부분 파싱이나 이미 노출된 선언은 거절한다. Ready를 부여하거나 원작업을 새 작업으로 대체하지 않으며 정상 same-operation forward finalization 경로를 유지한다.

## 전용 검증 자원의 적용 대기 NFS 복구 보완

기존 control-off writer가 커밋 전 TARGET witness를 저장하지 않아, 미노출 NFS의 정상 복구도 중단되는 경로를 실제 신규 SPARSE 테스트 자원에서 확인했다. 이후 모든 Native writer는 선택적 operation control과 관계없이 durable target witness → verify → commit 순서를 지킨다. 저장 실패 시 commit하지 않는다. rendered commit 소유권은 유지한다.

이미 witness 세 필드가 모두 누락된 경우 일반 requireTarget은 그대로 거절한다. 보호된 NEW private USER fixture 생성 permit/claim/receipt, 최초 단일 Allocated NFS 선언, 정확한 six-table TARGET/응답, VM 및 ROOT1/DATA1 전체 할당 tuple, 커밋 전 schema2 formatter receipt와 현재 물리 serial/FSUUID/BOOT, writer·formatter·logical lease 유휴를 매번 확인하는 제한 경로만 별도 late recovery authority를 저장한다. 누락된 과거 witness를 채우거나 기존 데이터/부분 formatter receipt로 이 경로를 확대하지 않는다.

생성 receipt에는 과거 guest BOOT/DMI/deviceId가 없다. 해당 기록이 있었다고 주장하지 않으며, 동일 BOOT의 precommit formatter receipt와 보호된 신규 단일 DATA 할당 및 현재 VM transport를 조합한 별도 권위로 한정한다. 실제 전체 데이터 hash 검증으로 표현하지 않는다.

Java11 직접 관련 5 suites/86 tests는 정상 Maven 빌드 및 실제 복구 인수와 구분한다. 실제 Runtime factory의 control-off RED → GREEN 순서 회귀, 실제 보호 생성 receipt와 DTO, partial/foreign ROOT·DATA·BOOT·lease·late snapshot drift 거절을 포함한다. 정상 배포는 Manager outer/anonymous family의 실제 바이트 차이와 새 validator만 비교하여 반영하며, 직접 javac 산출물을 사용하지 않는다.

## 100개 Export 구성 중 확인한 QGA 인자 길이 한계

실제 13번째 Export ACL 적용에서 QGA가 /bin/bash 실행 인자 길이 초과로 실패했다. 기존 NFS apply는 unmasked JSON을 base64로 변환해 단일 shell 인자에 포함했다. Export별 검사·디렉터리 생성 증거가 누적되므로 작은 구성에서 통과한 경로가 다수 Export에서 중단됐다. 실패 원작업은 rev42 RECOVERY_REQUIRED, Native는 current41 및 같은 op42 PREPARED 상태였으며 canary8은 재부팅 기준선과 동일했다.

UTF-8 payload가 32KiB를 초과하는 일반 Native 명령은 기존 anonymous memfd 및 32KiB 분할 전송 경로를 사용한다. 일반 Native stdin reader의 기존 8MiB 상한을 QGA 호출 전에 확인하며, 작은 요청·정적 네트워크 설치·기존 보호 payload의 의미는 유지한다. 설정 JSON을 줄이거나 검사 증거를 버리지 않고 같은 바이트를 전달한다. Payload를 인자로 되돌리거나 디스크 파일로 대체하는 우회, 불확정 commit의 재전송은 허용하지 않는다.

회귀는 13개 Export 크기의 인자 초과 재현, 전송 바이트 동일성, UTF-8 byte 경계, QGA 전 8MiB 거절, close-before-commit, 불확정 commit 1회 및 capability 미지원 시 중단을 포함한다. 이 변경은 KVM Wrapper에 국한되므로 정상 KVM 모듈을 다시 빌드하고 호스트의 해당 클래스만 교체한다. Native CODE3·SystemVM 이미지·관리 서버 및 DB 스키마 변경은 필요하지 않다.

원작업은 정상 reconcile의 exact SOURCE 복원 경로로 정리한다. ROLLED_BACK·기존 current41·pending 부재·ACL 부재·기존 데이터 보존을 확인하기 전에는 ACL 요청을 다시 제출하지 않는다. 정리 후 같은 Allocated Export에 새 명시적 ACL 요청을 적용하며 Export 재생성·DATA 재포맷은 하지 않는다.
