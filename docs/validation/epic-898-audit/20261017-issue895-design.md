# #895 데이터 보존·분리·삭제 수명주기 설계

현재 기본 PRESERVE/DELETE enum, dry-run 영향 계획, operation lock과 DATA identity 보호를 재사용한다. 새 이슈·브랜치·PR은 만들지 않고 Epic PR1271에 통합한다. 전체 UI 표준화1275는 HOLD다.

## 계획과 재시도

- 기본은 PRESERVE_VOLUMES다. DELETE_VOLUMES는 정확한 서비스명, 현재 승인한 plan hash와 별도 최종 데이터 손실 확인을 요구한다.
- DATA 계획의 권위는 UUID/type/account/domain/zone/pool/size와 서비스/VM 관계다. 프로젝트는 해당 소유 계정의 접근 범위로 검증하며 표시 정보를 위해 기존 DATA hash 계약을 변경하지 않는다. 표시용 ROOT·기본/추가 DATA·프로토콜·범위 정보를 보완하되 DATA 계획의 hash를 임의로 약화하지 않는다.
- 효과가 시작된 뒤 같은 서비스·정책·hash의 재시도는 원래 고정 계획을 사용한다. 현재 활성 행만으로 새 계획을 만들어 이전 승인이나 완료 receipt를 덮어쓰지 않는다.
- 정상 부분 detach·이미 완료한 삭제는 원래 identity의 IncludingRemoved 조회로 재검증한다. 새로운/누락된/외부 소유/교체된 DATA와 계획 변경은 거절한다.
- provider 효과 완료를 영속 기록한 다음 COMPLETE audit·서비스 행 제거를 진행한다. 감사/DAO 실패를 성공으로 반환하지 않으며 완료 receipt가 있는 재시도는 provider 효과를 반복하지 않는다.

## 데이터 보호와 효과 순서

- 관리 writer 미해결·미검증 format intent·unknown Native journal은 lifecycle 효과 전에 차단한다. Running과 Stopped를 구분해도 미완료 포맷을 성공으로 승격하지 않는다.
- 실제 부재인 legacy journal과 손상된 journal/parent·symlink·hardlink를 구분한다. 새 포맷·repair·자동 재포맷은 추가하지 않는다.
- 기존 provider의 정상 shutdown→Stopped 검증→DATA detach→VM expunge 순서를 재사용한다. 전원이 정지된 상태에서 분리하며, guest unmount API를 별도로 실행한 것으로 주장하지 않는다.
- DATA detach 실패는 남은 DATA 삭제·VM expunge·서비스 행 제거를 중단한다. ROOT는 서비스 VM의 수명주기를 따르며 보존 대상 DATA와 구분해 표시한다.
- 보존된 DATA는 소유·도메인·프로젝트·zone·풀·크기와 기존 FS/파일을 유지한다. 재사용은 MOUNT_EXISTING으로만 수행한다.

## UI 동작

- 첫 화면은 보존 기본값과 ROOT/DATA·프로토콜/소유 영향 목록을 보여준다.
- 파괴적 삭제는 영향 확인 후 별도 최종 확인을 거친다. plan/정책/서비스 범위가 바뀌면 기존 확인을 재사용하지 않는다.
- accepted job은 완료까지 추적한다. 조회 실패·불명확 상태에서는 같은 job 재조회만 허용하고 새 POST를 자동 전송하지 않는다.
- 부분 실패의 정상 재시도와 불명확 작업의 재전송을 구분한다. 전반적인 탭/대화상자 레이아웃 정리는 하지 않는다.

## 인수 계획과 보호 경계

새 전용 서비스와 SPARSE 이상 ROOT/DATA만 만든다. 실제 기본 보존, soft destroy/recover/start, 다중 볼륨 보존·재사용, DELETE의 명시적 확인과 물리 부재, 부분 detach 실패 후 동일 계획 재시도, 감사/DAO 경계와 권한을 검증한다. 각 항목은 단위/회귀·실제 API·실제 UI 수준을 구분하고 미수행 사항을 성공으로 확대하지 않는다.

실제 부분 실패 주입은 정확한 own DATA 행의 유한 잠금처럼 기존 자원을 변경하지 않는 방법을 우선하며, 자동 해제·알려진 job 추적·재시도 재전송0을 보장한다. 제품 영구 fault flag나 새 공개 API는 추가하지 않는다.

기존 보호 Before collector는 API와 호스트3개 읽기로 PASS했다. baseline SHA099076b3aa89c2d2889493d7c291d41aa93a363f937bf06a473cc2fbccacfc0f. F1/ref59/ret61 및 복구 필요10행은 원본과 대조한다. partial021b는 API/DB-only이며 직접 guest/QGA/ARP/format/mount/repair/detach/delete/reboot는0이다.

검증된 private USER eb61/source1acf 이미지를 base로 사용하고 #895 최종 Native를 정상 TEST 서명 CODE3로 업그레이드한다. 최신 전체 템플릿 교체나 운영 서명키 전환으로 확대하지 않는다. 자격증명은 런타임에서만 사용한다.

## 최초 빈 SMB SOURCE의 실제 복구 경계

13번 전용 시험 VM에서 첫 SMB 활성화가 DATA 포맷 전에 실패했다. 아직 Samba가 실행된 적 없는 초기 상태에서 smbstatus가 rc=0과 빈 sessions/tcons를 반환하더라도 open_files를 생략할 수 있다. 일반 세션 조회의 UNKNOWN을 빈 상태로 바꾸지 않고, 다음 초기 SOURCE의 실제 부재를 별도로 검증한다.

- current 파일 부재, revision 1의 정확한 PREPARED pending, 원래 BOOT·SOURCE 7개 선언·설정 해시 일치를 요구한다.
- SMB 선언·활성 unit·소유 endpoint·데이터베이스가 없고, 새 stopped 관측에서 daemon·listener·connection·holder와 DB가 모두 부재여야 한다. dangling DB symlink는 부재로 인정하지 않는다.
- 기존 검증된 revision의 엄격한 inspect 경로는 그대로 유지한다.
- 이미 실패해 원래 서명 CLI475dc43c…의 checkpoint를 가진 초기 SOURCE는 원래/현재의 서명된 설치 영수증과 전체 원본 바이트를 검증한다. 두 heredoc의 stable_sessions_empty·기존 두 bridge 메서드·해당 pin 선언 외 바이트 변경은 허용하지 않는다.
- 상태 조회는 복구 가능성만 판정한다. 원래 scope·공개키·cipher·SOURCE 및 빈 SMB identity를 인증하고 실제 writer FD9를 보유한 import만 기존 immutable 호환 영수증을 최초 한 번 발행한다.
- 일반 frozen·code_compatibility·import·stop 알고리즘의 권위를 낮추거나 journal·DB·구성·코드 pin을 수동 변경하지 않는다.

실제 실패 및 실패한 원래 CLI의 정상 reconcile 결과는 보존한다. 새 코드의 실제 정상 upgrade·같은 operation 복구와 기능 인수 결과는 별도 검증 기록에서 확정한다.
