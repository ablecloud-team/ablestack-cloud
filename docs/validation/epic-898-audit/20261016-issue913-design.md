# #913 네트워크 준비·기본 경로 지속성 설계

기존 Epic 브랜치와 SharedFS 네트워크 입력/저장 구조를 재사용한다. 최신 upstream4bd1a2cff50을 로컬 ablestack-europa에 먼저 반영해0/0을 확인했으며 시작 commit은343ba01858a이다. 새 이슈·브랜치·PR은 만들지 않고 기존 Epic PR1271에 통합한다. 최종 UI 표준 정리1275는 미착수다.

## 재사용 및 실제 보완

- SharedFSServiceImpl의 gateway 특수주소·CIDR·self/network/broadcast 거절, STATIC primary 보호, 정식 NIC CAS 복구를 재사용한다. 같은 CIDR 안의 특수주소와 primary/alias 보존 회귀를 추가한다.
- 기존 VM의 구형 init.sh SharedFS 분기도 정적 상태 파일이 있으면 setup_common을 실행하지 않도록 정확한 기존 분기만 교정한다. monitor/init 두 파일을 모두 사전 검증하고 이미 교정됐으면 inode를 바꾸지 않는다. 다른 역할·설정은 보존하며 알 수 없는 형태는 변경하지 않는다.
- 현재 KVM QGA가 설치하는 inline helper/unit은 최신 부팅 경로와 다르다. canonical 네트워크 helper와 network/reconcile/DHCP 유닛4개를 template source에서 단일 관리하고 KVM resource에 같은 바이트로 포함한다. 실제 배포도 wrapper와 이 resource만 기존 호스트 JAR에 반영한다.
- 상태 파일의 schema1/mode를 지원하고 기존 mode 없는 STATIC JSON도 읽는다. 유효한 STATIC 상태를 읽을 수 없으면 DHCP로 임의 전환하지 않는다. mode 없는 상태 파일 부재만 기존 DHCP 준비 경로로 처리한다.
- MAC으로 NIC를 찾고 STATIC IP/prefix·connected route·선택 gateway/DNS를 적용한다. 이미 일치하는 primary/alias와 route는 유지하며 다른 NIC는 변경하지 않는다. gateway가 없으면 해당 NIC에 default route가 없어야 한다.
- STATIC NIC의 DHCP unit을 stop/mask하고 실제 dhclient를 정확한 NIC·argv·root executable·PID/startTicks·network namespace에 결합해 종료한다. 다른 NIC/namespace의 DHCP는 제외한다.
- network readiness는 cloud-preinit 이후 실행되며 Storage reconcile은 준비 성공 후 실행한다. QGA는 네트워크 준비와 독립해 L2 첫 부팅에서 STATIC JSON 주입이 가능해야 한다. 진행 중 DHCP 대기는 유한하며 STATIC 주입 뒤 수렴한다. 부팅 의존성 cycle을 실제 systemd 검사와 새 VM 부팅에서 확인한다.
- 적용/읽기 검증에 같은 effective DNS 정책을 사용한다. 정상 AD JOINED 설정이 소유하는 DNS는 static fallback보다 우선하며 이번 이슈에서 AD 가입/탈퇴는 수행하지 않는다.
- monitor에 schema1 networkReadiness를 추가한다. expected/actual mode·MAC·IP·prefix·gateway·DNS·NIC·DHCP unit/process·관측시각과 mismatch를 제공한다. 관측 불능은 UNKNOWN, 확인한 불일치는 ERROR로 표시한다. API의 기존 health cache를 통해 UI에 전달한다.
- UI는 기존 STATIC 선언 정보를 유지하고 실제 관측과 불일치 원인을 보완한다. 잘못된 gateway 입력을 차단하고 monitor ERROR를 정상 초록색으로 표시하지 않는다. 전체 상세 화면 레이아웃은 변경하지 않는다.

## 배포와 실제 인수

기존 템플릿의 전용 VM65(10.10.13.236/16, gateway10.10.0.1, ROOT/DATA SPARSE)를 만들어 QGA 교정 전후와 정상 재부팅을 검증한다. 새 helper/unit이 포함된 정규 Packer SystemVM 이미지는 고정 source·SPARSE metadata preallocation·RAM 전용 TEST 서명으로 빌드하고 독립 이미지 readback 뒤 private 시험 템플릿으로 등록한다. 운영 기본 템플릿을 교체하지 않는다.

| 게이트 | 확인할 증거 |
|---|---|
| STATIC+gateway | 생성 직후와 정상 재부팅 후 MAC/IP/prefix/정확한 default route/DNS 유지 |
| protocol 복구 | 동일 DATA/파일·Native generation을 보존하며 NFS/SMB/iSCSI/NVMe-oF listener와 자원 복구 |
| DHCP 충돌 | exactNIC unit 재시작 차단, 잔존 프로세스 종료, 실제 짧은 lease 갱신 경계를 넘는 STATIC 유지 |
| no gateway | 새 시험 VM에서 connected route만 존재, 해당 NIC default 없음 |
| DHCP | 기존 격리망의 정상 DHCP 생성·재부팅·주소/route/DNS 복구 |
| 다른 NIC명 | MAC으로 eth0 이외 NIC를 찾아 실제 네트워크 적용/검증 |
| invalid gateway | self/network/broadcast/offCIDR/0/loopback/linklocal/multicast를 API 및 실제 UI에서 거절 |
| 오류·복구 | 소유 시험 VM만 route 불일치를 주입, monitor/API/실제 UI ERROR 후 정식 helper로 복구 |
| 기존 VM | 실제 QGA installer의 제한 경로로 교정, 기존 서비스 PID/IO/파일/설정 보존 |
| 신규 template | helper/unit/source manifest 일치, fresh boot의 network→reconcile 순서와 STATIC/DHCP 동작 확인 |

파일·자원 생성은 이슈 전용 scope로 제한한다. 신규 디스크는 SPARSE/FAT만 사용하고 THIN은 만들지 않는다. 원본 F1/VM54, 보호 partial021b/VM51, ref59 및 복구 검토 VM61은 조회로만 보존을 확인한다. 기존 복구 필요10행과 전역 용량 설정도 유지한다. 네트워크/템플릿 문제를 다른 신규 이슈로 분기하지 않고 이 이슈의 실제 완료 게이트와 남은 상태를 기록한다.

## 기존 VM의 빈 상태 파일과 초기 DHCP 분기

기존 sharedfsvm 초기화의 -s sharedfs-network.json 분기는 빈 파일을 DHCP 허용으로 판정하고 helper 실패를 무시할 수 있다. QGA 호환 설치는 실제 검증한 기존 네트워크 블록만 현재 템플릿과 동일한 QGA 활성화 및 ablestack-sharedfs-network --prepare || exit 1로 교정한다. 따라서 파일 부재의 DHCP와 정상·잘못된 STATIC 판정은 모두 canonical helper가 담당한다. 임의의 초기화 스크립트를 통째로 교체하지 않으며, 알 수 없는·중복된 네트워크 writer는 monitor/init 파일을 게시하기 전에 거절한다.

이 보완은 KVM 설치 코드와 전체 legacy script 회귀만 변경한다. Native helper·unit·CODE3와 UI 소스는 동결한 기존 바이트를 유지하므로 템플릿은 Native source c1a93ca2, UI는 6bf96d62, 최종 KVM 모듈은 후속 별도 소스 pin으로 검증한다. 기존 증거를 새 소스의 빌드로 재표기하지 않는다.


## 재부팅 인수에서 확인한 NVMe 관측 경로 보존

실제 legacy 시험 VM65의 정상 재부팅에서 네트워크와 네 프로토콜, NFS/SMB I/O는 정상 복구됐다. 그러나 커널의 디바이스 재열거로 NVMe namespace의 runtime.backingPath가 /dev/sdd에서 /dev/sda로 바뀌었고 boot apply가 이를 canonical nvmeof JSON에 저장했다. Native current 및 immutable VERIFIED artifact의 구성 해시는 77ee9627…인데 재관측 해시는 77ca6b13…가 되어 UNVERIFIED로 판정됐다. 전체7개 구성에서 그 단일 경로만 이전 값으로 메모리에서 치환하면 기존 확정 해시와 정확히 일치한다. 실제 볼륨 UUID·serial·크기·configfs 연결은 동일하다.

이 코드와 generation 모듈은 #913 이전 commit343ba018과 byte-exact다. 기존 결함이지만 후속 일반 writer가 IN_SYNC 경계에서 차단되므로, 네트워크·재부팅 인수와 함께 같은 이슈에서 보완한다. 단순 테스트 예외로 합격 처리하거나 별도 이슈를 분기하지 않는다.

### 정상 boot replay의 canonical 구성 보존

고정 canonical nvmeof 파일 자체를 보호된 FD9 writer 문맥으로 다시 적용할 때만 재저장을 생략한다. 실제 same-file·root 소유·안전한 mode·경로/열린 파일 identity를 확인한다. 일반 API의 별도 memfd payload는 기존대로 저장한다.

커널 장치 재발견, volume identity resolver, NVMe runtime identity, 인증 vault 및 kernel 적용·검증은 유지한다. 저장된 runtime 경로는 승인 당시 관측으로 보존하며 실제 API/UI 관측은 기존 configfs 기반 enrich가 현재 장치 경로와 정확한 볼륨 매핑을 읽는다. 전역 digest/redact 규칙과 ROOT_SOURCE_REPLAY 환경 예외는 변경하지 않는다.

### 이미 발생한 단일 관측 경로 drift의 제한된 복구

복구는 expected current scope/revision/BOOT와 immutable VERIFIED artifact의 정확한 checksum·전체7개 구성을 요구한다. pending/lease가 없고 전체 구성 차이가 정확히 하나의 소유 namespace.runtime.backingPath에 한정돼야 한다. NQN·namespace·volume UUID·serial·크기·실제 configfs enable 및 device 연결을 다시 검증한 뒤 그 관측값만 확정 artifact의 값으로 원자 복원한다.

Native current·revision·digest 규칙·데이터·인증 cipher는 변경하지 않는다. 다른 필드 변경, 불명확한 장치 매핑, 외부 namespace, 잘못된 artifact, 소유권/파일 identity 변동 및 동시 writer는 거절하고 원본을 보존한다. 일반 경로를 임의 baseline 채택이나 SOURCE 권한 우회에 사용하지 않는다.

### 추가 검증

새 helper/CLI embed 계약과 replay·복구 경계의 실패 회귀를 검사한다. 실제 소유 VM65에 새 소스의 정상 서명 CODE를 적용한 뒤 같은 artifact 복구의 Native IN_SYNC와 기존 current·DATA·cipher 보존을 확인한다. 이어 정상 API writer 성공과 재부팅·동일 인증정보 NFS/SMB I/O·네 프로토콜·기본 경로 및 Native IN_SYNC를 검증한다.

보완 전 C1 이미지와 실패 proof는 이력으로 보존한다. 보완 소스의 새 전체 SystemVM 빌드·서명·읽기 전용 이미지 검증·정상 private USER 등록을 마친 뒤 신규 STATIC/no-GW/no-DNS와 DHCP 생성·재부팅·API/실제 UI를 최종 인수한다. 보호 원본 및 부분 포맷 DATA는 이 복구의 대상이 아니다.


## 신규 템플릿 실측 보완: cloud-init 후속 DHCP 재개입

신규 STATIC/no-GW 전용 VM의 cold boot에서 network-ready는 약 5.6초, 초기화는 약 8초에 끝났으나, cloud-init.service가 약 132초에 직접 dhclient를 실행해 별도 DHCP 주소와 default route를 다시 추가했다. DHCP systemd unit이 masked이고 해당 프로세스가 이미 종료된 뒤에도 이 경로는 남을 수 있다. 따라서 초기 성공과 unit mask만으로 지속 상태를 판정하지 않는다.

정식 helper의 --prepare에서 SharedFS 역할을 확인하고 전용 cloud.cfg.d 파일을 원자적으로 설치한다. 네트워크 렌더링(network.config=disabled)과 활성화(disable_network_activation=true)를 함께 막고 로컬 NoCloud/ConfigDrive만 사용한다. 기존 postinit의 NoCloud 사용자 데이터 seed 및 config/final 모듈 실행은 유지한다. 다른 System VM 역할에는 이 설정을 만들지 않으며 --inspect는 읽기 전용이다. 기존 경로·다른 설정 파일을 일괄 변경하지 않는다.

실제 설치된 cloud-init 22 계열의 _find_networking_config 및 _should_bring_up_interfaces 구현을 확인한다. 새 데이터소스 선택뿐 아니라 기존 데이터소스 캐시가 복원된 경우에도 네트워크 apply와 활성화를 하지 않아야 한다. 공식 설정 근거: [cloud-init 네트워크 구성 문서](https://docs.cloud-init.io/en/22.4.2/topics/network-config.html).

신규 STATIC/no-GW 및 DHCP의 실제 health 응답은 null인 기대값 키를 생략한다. UI는 STATIC의 선택 gateway와 DHCP의 선택 MAC/IP/CIDR/gateway 키 생략만 지역적으로 null로 해석한다. 원본 응답, 명시된 잘못된 타입, STATIC 필수 필드, 실제 관측 필드, status/success 및 stale 검증은 유지한다. 이는 상태 표시 수정이며 #1275 최종 레이아웃 정리는 아니다.

최종 인수는 재부팅 직후에만 확인하지 않고, 이번 재현 시점인 부팅 약 132초를 지난 뒤에도 주소·경로·DHCP 소유 상태가 유지되는지 API와 실제 UI로 검증한다.
