# #918 제한 NFS ACL과 export 동적 갱신의 장애 격리 설계

## 현재 범위

기존 Epic #898 브랜치 epic/898-sharedfs와 Draft PR #1271에서만 진행한다. 기준 소스 cbedf8419d455d82ecddef61ff5502642220db4a와 local/origin/upstream ablestack-europa dc31262567f2afe5f6278fae61c1cef7e307fe3e의 동기화를 확인했다. 새 이슈·브랜치·PR을 만들지 않는다. #1275 최종 UI 표준화는 보류한다.

이슈 원문, 추가 DBus UpdateExport 실증과 실제 /32 부분 검증 기록을 현재 코드에 대조했다. 기존 ganesha_dbus.py의 동적 갱신과 nfs_readiness.py의 SKIPPED_ACL을 재사용한다. 과거 부분 실증을 이번 전체 인수로 간주하지 않는다.

## 확인한 보완점

- 제한 ACL에 로컬 소스가 없을 때 success=None/문자열 사유만 남겨 명시적 probe 생략과 실제 실패의 구분이 부족하다.
- DBus 갱신이 성공해도 모든 export를 다시 mount 검사해 다른 export의 지연·오류가 해당 ACL 작업을 실패시킬 수 있다.
- 동적 갱신의 대상 Export_Id 집합·변경 블록·ACK·실효 ACL/PID/listener 검증과 실패 복원 조건을 강화해야 한다.
- health와 NFS 표에 현재 권위에 결합된 로컬 probe 판정·생략 사유와 실제 client ACL을 함께 제시할 근거가 필요하다.

## 판정과 원자성

로컬 IPv4 관측이 성공하고 ACL 자체가 유효하며 허용된 로컬 소스만 없는 경우에 한해 ACL_RESTRICTED_NO_LOCAL_SOURCE로 생략한다. config·managed PID/startTicks·owned listener·정확한 runtime export inventory 검증은 그대로 요구한다. 주소 관측 실패, malformed ACL, 실제 mount/cleanup 실패를 생략으로 바꾸지 않는다. SystemVM IP를 client ACL에 추가하지 않는다.

일반 NFS API의 기존 operationScope·PendingNfsAuthorization·실제 FD9/FLOCK와 current 전체5필드·immutable VERIFIED 일곱 desired 파일 SHA를 재사용한다. 특수 ALL4 renderedValidationProfile 활성화 없이 일반 경로에서 동적 적용을 지원한다. 기존 pure renderer로 SOURCE/TARGET을 비교하고 현재 SOURCE raw config·동일 PID/startTicks·owned listener·DBus inventory와 ACL이 모두 일치할 때만 private snapshot을 만든다. 동적 TARGET 게시에는 SOURCE CAS·atomic replace·fsync를 사용하며 부분 갱신 실패는 원래 SOURCE와 해당 작업 TARGET으로 확인된 runtime만 보상한다.

동일 listener/core/protocol·같은 Export_Id 집합과 path/pseudo/FSAL의 기존 export ACL/access/squash 변경은 변경 블록만 UpdateExport한다. ACK와 ShowExports/DisplayExport의 실효 client/권한을 검증하고 동일 PID/startTicks·owned listener를 확인한다. 성공은 DBUS_DYNAMIC_UPDATE_VERIFIED로 표현하며 전체 mount probe를 수행하지 않는다. no-op도 runtime 검증을 수행한다.

export 추가/삭제 또는 endpoint/core 구조 변경은 기존 엄격한 전체 적용 경로를 유지한다. 동적 적용 대상의 DBus 호출·readback 실패는 새 TARGET을 재기동해 성공 처리하지 않는다. 이전 설정과 runtime export를 복원한 뒤 관리 작업은 실패 처리하며 #892 generation·SOURCE·writer/lease·idempotency 권위를 유지한다. 일반 export probe 실패를 유효한 endpoint 자체 장애와 분리한다.

## API·UI 계약

기존 API resultjson 전달과 민감 필드 제거를 재사용한다. 새 DTO·DDL·공개 API를 추가하지 않는다. Backend는 실제 response serializer 경유 성공/실패/null·민감 값 제거 회귀로 기존 gate를 확인한다.

health.nfsGanesha.endpoints[].probeResults[]에 exportUuid/exportName, success/status, probeSkipped, skipReason, 실제 canonical clients를 표시한다. probeObservationVerified는 BOOT/config SHA/PID/startTicks/owned listener와 정확한 DBus inventory가 결합된 관측에만 true다. 생략 사유는 ACL_RESTRICTED_NO_LOCAL_SOURCE 또는 DBUS_DYNAMIC_UPDATE_VERIFIED다. stale/관측 불능은 미확인이며 실제 실패가 생략 사유보다 우선한다.

필요한 마지막 적용 증거는 크기·행 수가 제한된 atomic /run receipt로 결합하고 현재 권위와 일치할 때만 게시한다. 이 증거는 외부 클라이언트 I/O 완료를 뜻하지 않는다. 기존 NFS export 표에 기능 상태와 client ACL만 추가하고 폼·탭·대화상자 레이아웃은 재구성하지 않는다.

#914의 작업량 기반 내부600~1500초/systemd1800초, 구조화 실패·child/mount 정리와 protocol별 완료 상태 의미를 유지한다.

## 검토 중 발견한 추가 실패 경계

실제 DBus 검증 뒤 과거 startup 로그 문자열만으로 healthy PID를 중지하지 않는다. 최신 RPC readiness까지 통과한 뒤에만 TARGET을 VERIFIED로 표시하며, 늦은 실패도 SOURCE 보상 대상이다.

새 snapshot 쓰기 중 실패하면 같은 프로세스가 O_EXCL로 생성한 정확한 파일과 inode만 정리한다. 알 수 없는 crash·예상 밖 파일은 보존한다. 유효한 PUBLISHING checkpoint도 동일 scope/BOOT/frozen SOURCE에 한해 복구한다. 정상 commit으로 확인된 predecessor snapshot만 후속 writer가 정리한다.

## 13번 실제 검증

기존 자원은 읽기 전용 보호 대상으로 유지한다. partial021b는 API/DB metadata만 관측하며 guest/ARP/format/mount/repair/detach/delete/reboot를 수행하지 않는다. 새 전용1VM의 ROOT와20GiB DATA는 SPARSE·전체 필요 L2 할당·noBacking을 확인한다. 기존 private TEST 이미지에서 정상 runtime CODE 경로로 해당 구현을 갱신한다.

1. wildcard 및 로컬 CIDR은 기존 mount probe를 실제 수행한다.
2. 외부 클라이언트1의 /32만 허용하고 SystemVM IP가 없는 ACL로 정상 적용한다.
3. 허용 클라이언트의 NFSv3/v4 실제 mount·파일 생성/fsync/읽기와 비허용 SystemVM/클라이언트2의 접근 거부를 확인한다.
4. client2 추가/제외, 다중 CIDR 및 squash/access 변경 전후에 DB·saved desired·config·runtime ACL/revision 일치를 확인한다.
5. 유지되는 클라이언트의 열린 NFSv4 세션과 연속 I/O·같은 Ganesha PID/listener·다른 export의 구성과 I/O를 확인한다.
6. 동적 성공 중 관계없는 mount probe 호출0을 확인하고 여러 export 환경의 실제 소요를 기록한다.
7. disposable 자원에만 bounded DBus 실패·readback 불일치·일반 probe 실패를 주입해 SOURCE rollback·API job 실패 및 정상 export 보존을 검증한다.
8. 재적용과 정상 재부팅 후 동일 ACL·NFSv3/v4 I/O·monitor/API/실제 UI 상태를 확인한다.
9. 실제 UI에서 ACL 변경 요청과 정상/생략/실패/미확인 문구를 검증한다. API 성공만으로 UI 검증을 대체하지 않는다.
10. 전용 actor·시험 장치를 종료하고 정상 destroy/expunge/delete API로 전용 자원을 정리한다. API와 호스트3대의 정확한 domain/backing 부재 및 원본 보존을 독립 관측한다.
