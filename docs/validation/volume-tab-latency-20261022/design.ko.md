# 상세 이벤트·코멘트 탭 로딩 지연 개선

대상: 볼륨·컴퓨트 오퍼링·디스크 오퍼링 상세, Epic #1422 / Draft PR #1435 후속 보완.

## 재현과 원인

31·32번에서 공통 탭 모듈이 이미 로드된 상태로 상세의 이벤트·코멘트를 처음 열면 약 10.2초 동안 로딩한다. 첫 API는 HTTP 200으로 약 0.1초에 완료되지만 화면은 약 10초 뒤 같은 API를 다시 호출한 뒤 표시한다. 일부 첫 모듈 로드는 정상적으로 빠르므로 단순 최초 접속만으로는 놓칠 수 있다. 가상머신의 같은 탭은 약 0.6초에 표시했다.

ResourceView는 activeTab을 먼저 변경해 탭 컴포넌트를 생성한 뒤 router.push로 query.tab을 갱신한다. listRefreshMixin은 전체 URL을 요청 소유 범위에 포함한다. 따라서 첫 요청이 시작된 뒤 URL이 커밋되면 정상 응답과 finally의 로딩 해제를 이전 범위의 응답으로 폐기한다. 부모 상세도 탭만 바뀐 경우 재조회하지 않으므로 다음 10초 주기의 탭 자동 갱신까지 기다린다. 가상머신은 이 탭 전환에서 기존 history 경로를 사용한다.

## 구현 계약

- listRefreshMixin에 명시적인 routeKey 옵션을 추가한다. 기존 어댑터의 기본값은 전체 URL을 유지한다.
- 공통 EventsTab·AnnotationsTab만 detailTabRouteKey를 사용한다. 경로와 tab 이외의 모든 query를 유지하며 표시용 tab만 제외한다.
- 자원·사용자·프로젝트·페이지 등 기존 소유 범위와 in-flight 중복 요청 병합, 실패 시 기존 행 보존은 유지한다.
- 응답을 늦추거나 10초 타이머 주기를 줄이는 대신 첫 정상 응답으로 표시하고 로딩을 끝낸다. API·DB·스토리지 엔진 변경은 필요하지 않다.

## 검증

수정 전 코드에서 세 메뉴 × 두 공통 탭의 지연 회귀 테스트 6개가 실패함을 확인했다. 수정 후 탭 URL 전환 중 응답·빈 목록·중복 호출 병합과 자원/프로젝트/사용자/페이지/query 변경의 이전 응답 차단을 검증한다. 기본 어댑터가 여전히 전체 URL을 사용하는지도 확인한다.

31·32의 전용 볼륨·컴퓨트/디스크 오퍼링과 코멘트를 사용해 클릭→로딩 해제 시간, API 시간·요청 수·자원 범위를 전후 비교한다. 가상머신은 기존 자원을 읽기 전용으로 비교하며 데이터를 변경하지 않는다. 빌드는 UI만 표준 최적화로 수행하고, 정적 배포 때 서버 파일·JAR·PID·설정을 보존한다. 모든 전용 자원은 검증 후 API로 정리하고 운영 inventory와 비교한다.
