# #1210 개별 기능 검증 절차

1. 31 GFS2 / 32 RBD에서 운영 VM·볼륨·활성 오퍼링 inventory와 관리 PID/JAR 해시를 별도 보존한다.
2. 전용 도메인·User/DomainAdmin·프로젝트, 공개 thin 오퍼링, 독립 네트워크와 VM 3개씩을 생성한다. 일반 계정의 두 VM은 서로 다른 이름/UUID와 동일한 변경된 표시이름을 갖는다. 하나는 Running, 하나는 Stopped다. 프로젝트 VM은 별도 표시이름/범위다. 최초 기동 전 Stopped + Allocated 연결은 #1471 NPE로 실패한 독립 사례로 보존한다. 최초 기동·정지 후의 프로젝트 연결은 별도 준비 조건에서 수행한다.
3. 수정 전 볼륨 연결 대화상자에서 변경된 표시이름을 검색해 데이터 없음 증상을 기록한다.
4. 소스의 표시이름 우선 표시·이름/인스턴스/UUID 보조 표시, 모든 상태별 페이지 조회, 원자적 목록 교체, 같은 범위 오류/재시도와 제출 전 UUID 재확인을 단위 검사한다.
5. UI만 WSL ext4에서 빌드하고 각 관리 서버의 활성 webapp에 정적 파일만 배포한다. WEB-INF/META-INF/config, 관리 JAR/PID를 보존하고 전체 파일 해시·FTCTL 마커·HTTP 200을 확인한다.
6. Admin의 일반 볼륨 연결에서 변경된 표시이름·VM 이름·인스턴스 이름·UUID·대소문자·검색 결과 없음/해제를 검사한다. 후보를 새로 조회한 뒤 동일 표시이름 두 후보가 UUID로 구별되는지 확인한다.
7. Running VM을 선택해 attachVolume POST의 UUID, API/DB 연결, Ready와 1GiB, 호스트 libvirt 디스크 source와 실제 GFS2 이미지/RBD 정보를 대조한다. 게스트 I/O는 이 이슈에서 주장하지 않는다.
8. 분리 후 같은 표시이름의 다른 Stopped VM UUID로 연결해 API/DB가 두 번째 UUID를 참조하는지 확인한다. User/DomainAdmin 계정의 후보 범위와 Project의 별도 후보·실제 연결을 확인한다.
9. 특정 listVirtualMachines XHR만 오류로 제어해 오류 표시·제출 차단·동일 대화상자 재시도와 세션 보존을 검사한다. 제어 응답은 실제 서버 결과와 구분한다.
10. 테스트 VM/볼륨·프로젝트·계정·네트워크·도메인 정리, 오퍼링 Inactive, API/DB 활성 잔여 0·물리 이미지/VM 정의 부재·운영 inventory 동일·호스트 Up을 확인한다. 제품 이력과 롤백 백업을 보존한다.
11. 최종 증거를 Epic PR #1435에 연결하고 #1210을 Completed로 닫는다. #1471 서버 결함 해결 → #1433 UI 표준 통일 → #1434 전체 통합 검증은 별도 완료 기준이다.

## 범위와 해석

- API/DB 대조, 브라우저 실제 동작, 제어 응답, 단위 검사/모듈 빌드, 전체 CI는 별도다.
- 100개 초과 VM 실환경 생성은 수행하지 않는다. 여러 API 페이지의 수집·부분 실패·늦은 응답은 단위 검사로 검증하고 실환경의 API page/pagesize 계약과 대조한다.
- Stopped/Allocated 연결은 Cloud의 할당·연결 계약만 확인하며 실물 디스크나 게스트 부팅 성공으로 확대하지 않는다.
- RBD는 확인된 RAW 경로만 기술한다. falloc/lazy thick·영구 예약을 주장하지 않는다.
