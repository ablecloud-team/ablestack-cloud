# #1486 구현 및 검증 결과

Epic #1473 / SS-13. 브랜치 `dhslove/epic-1473-storage-snapshots`, 시작 커밋 `5ed664e6c7e4d0cdcacc18794dddae3c405a16ff`.

## 구현

가상머신 상세의 공통 ResourceLayout(7:17), InfoCard, 상태, ID 복사, 소유자/도메인/생성일, 작업 영역과 태그를 재사용했다. 필드 간격 CSS를 분리해 VM과 스냅샷이 같은 라벨 굵기·5px 간격·20px 필드 여백을 사용한다. 오른쪽 상세의 중복 이름/ID/소유자/생성일을 제거하고 전용 속성 컴포넌트로 교체했다. 볼륨 상세 탭은 변경하지 않았다.

카드에는 가상 용량과 Secondary 백업 물리 크기, 현재 원본 볼륨/연결 VM, 사본 Zone을 표시한다. 상세는 번역한 수동/정기 유형, 주기, ROOT/DATA, 현재 원본 상태, 되돌리기 조건과 사본별 저장소·역할·상태·가용성·가상 용량을 표시한다. 0과 미확인을 구분하며, API가 제공하지 않는 사본별 물리 크기는 추정하지 않는다. 부모/체인은 기능 설정이 켜졌을 때만 표시한다.

논리 스냅샷, 전체 사본 페이지와 허용된 관련 자원을 하나의 상세 읽기로 검증한다. 식별자, 소유 범위, 사본 건수·중복과 부모 소유 관계가 어긋나면 오류로 처리한다. 새 대상/프로젝트/사용자/역할/API 권한/설정으로 이동하면 이전 응답을 무효화한다. 동일 대상의 일시 오류에서는 기존 카드·태그를 유지하고 스냅샷 작업을 잠근다. 접근 거부/소실 시 이전 정보를 비운다. 관련 볼륨 조회만 제한되면 해당 링크와 VM 링크를 제한한다. 삭제된 원본에도 복구 가능한 백업의 볼륨 생성 진입은 유지한다.

태그는 SS-11의 독립 조회·권한·범위·job 완료 추적을 그대로 사용한다. 상세 조회 실패와 태그 조회 실패는 구분하며, 태그 자체의 조회 실패에서는 기존 태그를 보존하고 변경을 차단한다. 새 대화상자는 추가하지 않았고 기존 표준 작업 대화상자는 유지했다. StorPool 전용 UI 옵션은 추가하지 않았다.

최종 소스의 집중 테스트 10개 묶음 / 162개 통과. lint와 production UI 빌드를 통과했다. 전체 Cloud 빌드, Maven 변경 모듈 빌드, GitHub Actions 실행은 요청·수행하지 않았다. 기존 Browserslist 및 번들 크기 경고는 로그에 남아 있다.

실제 UI에서 DATA/ROOT, 일반 소유자·다른 계정·프로젝트·도메인 관리자·읽기 전용 역할, 볼륨/VM/계정/도메인/Zone/Secondary 및 RBD Primary 링크 이동을 확인했다. 프로젝트 관련 링크에 projectid가 유지된다. 원본 삭제 사유와 볼륨 생성 메뉴 유지, 작은 물리 크기, 사본 ID/건수·역할도 실제 API/DB와 대조했다.

태그를 UI에서 생성·삭제하고 job 완료 후 수동 갱신 없이 반영되는 것을 확인했다. 생성 시 독립 SQL로 값이 존재하고 삭제 후 0건임을 확인했으며, 두 job의 async_job 상태는 성공(1)이다. 503, 403, 대상 0건, 사본 count 불일치, 관련 볼륨 403, 태그 조회 503, 대상 전환 뒤 늦은 응답은 명시적인 브라우저 응답 주입으로 검증했다. 백엔드 장애나 DB 불일치를 실제로 만들지 않았다. 각 주입을 제거한 뒤 정상 재조회로 복구했다.

12개 화면의 DOM 크기와 PNG 픽셀 너비를 비교했고 라벨/값 겹침 및 페이지 가로 넘침이 없었다. VM과 동일한 라벨 굵기와 간격을 확인하고 라이트·다크의 실제 화면을 검토했다. 원래 다크 테마, 기본 소유 범위, 빈 검색으로 복귀하고 viewport/네트워크 주입과 임시 탭을 정리했다.

## 검증 한계

- 두 클러스터의 전용/기존 스냅샷에는 실제 부모 체인이 없었다. 실제 API의 체인 누락·미확인을 확인했고, 양성 부모 링크·체인 크기 및 0/미확인 경계는 **응답 주입**으로 검증했다. 실제 부모 조회/이동은 수행했으며 DB 체인은 변경하지 않았다. 실물 체인 생성·누적 크기 검증으로 보고하지 않는다.
- 사본별 physicalsize는 실제 API에 없다. 전체 Secondary 백업 물리 크기는 실제 파일 바이트 길이와 일치한다. qemu-img의 할당 크기는 파일 바이트 길이와 다른 개념으로 따로 기록했다.
- 기존 공통 ID 복사 버튼의 키보드/클릭 실행과 성공 안내는 확인했다. 자동화 브라우저의 클립보드 읽기 값이 비어 있어 **실제 OS 클립보드 바이트 복사는 확인하지 못했다**. 성공 안내를 바이트 검증으로 간주하지 않는다.
- 이번 검증은 SS-13 범위이며 전체 Cloud CI나 #1489 통합 회귀의 완료를 의미하지 않는다.

## 배포와 정리

동일한 최종 UI 자산 924개를 두 관리 서버의 활성 webapp에 배포했다. 파일별 SHA-256과 새 마커를 확인하고 WEB-INF/META-INF, 설정, 관리 JAR, 기존 대용량 파일을 보존했다. 서비스 재시작 없이 Mold active, `/client/` HTTP 200을 확인했다. 배포 백업은 각 서버 `/nfs/snapshot-detail-1486-20261025-ui-backup`에 보존했다.

각 클러스터의 전용 스냅샷 7개, 추적 볼륨 6개(ROOT 포함), VM 1개, 프로젝트 1개, 계정 3개, 도메인·읽기 전용 역할을 정상 API로 정리했다. 삭제는 dryrun 범위 해시를 확인했으며 강제 삭제/수동 DB 삭제는 사용하지 않았다. 체인 설정은 원래 false로 복원했다. 정상 삭제의 Destroyed/removed 이력은 보존한다. 활성 snapshot/ref/volume/tag/policy/schedule/VM/account/domain/project/role은 0이고 Secondary 파일·GFS2 볼륨 또는 RBD live/trash, 모든 호스트의 전용 libvirt VM 잔여도 없다.

기존 볼륨·스냅샷·VM·오퍼링·Zone·스토리지·호스트·Secondary의 비교 필드 및 Windows/WSL 기본 FT 작업 디렉터리의 HEAD/status/diff는 변경되지 않았다. 원본 dirty diff를 공개 증거에 포함하지 않고 비교 해시와 보존 판정만 저장했다.
