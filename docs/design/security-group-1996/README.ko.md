# Mold 보안 그룹 개선 작업 계획

[상위 Epic #1996](https://github.com/ablecloud-team/ablestack-cloud/issues/1996)

이 계획은 Europa 기준 커밋 `ee6c5da5f1f686c6f0726b628ee873fe44b4cbb6`에서 시작한다. 31번 GFS2와 32번 RBD의 Native KVM Shared Network 및 Mold UI를 대상으로 한다.

## 실검증에서 확인한 범위

- 31번 VLAN 160, 32번 VLAN 161과 두 클러스터의 untagged에서 총 12대의 시험 VM을 사용했다. 같은 호스트의 실제 IPv4 TCP·UDP 시험에서 다른 계정에서 시작한 48개 연결에 수신 서비스가 모두 응답했다.
- 관리 서버에 수신 규칙이 저장되고 대표 호스트의 VM 규칙이 생성됐지만 수신 실측은 허용 범위와 달랐다. 확인한 호스트의 설치 스크립트는 이미 병합된 수정 직전 버전이었다. 두 관찰의 인과는 일치하는 설치본에서 다시 검증한다. [기존 호스트 수정 PR #1515](https://github.com/ablecloud-team/ablestack-cloud/pull/1515)
- 시험망을 삭제한 후 호스트에 시험 브리지 전용 IPv4·IPv6 규칙이 남았다. 해당 규칙을 정리한 후 지정 호스트의 FORWARD 규칙은 시험 전과 일치했다. 조회 기준 기존 VM 221대의 상태·호스트·NIC·보안 그룹 연결은 전후 동일했다.
- VM 보안 그룹 창의 소유자 조회는 브라우저의 연결 상태를 모의하고 실제 API 요청으로 확인했다. 라우터 없는 오퍼링의 필수 검사와 31번 시작 작업의 ConfigDrive 오류는 실제 UI 실행에서 확인했다.

## 검증 기준

| 조건 | 기대 결과 |
| --- | --- |
| 수신 규칙이 없는 새 연결 | 같은 그룹 및 다른 계정에서 모두 기본 차단 |
| 그룹 또는 CIDR 기준 제한 수신 | 소스와 프로토콜·포트가 허용된 경우에만 성공 |
| 발신 허용, 수신 차단 | 상대 VM의 수신 정책을 그대로 적용 |
| 규칙 회수·마지막 NIC 제거 | 새 연결은 기본 정책으로 돌아가고 시험 브리지 참조가 회수됨 |
| 비대상 제어 VM | 정책 적용 전·중·후 기존 연결과 신규 서비스 연결 유지 |

실제 UI 작업 ID, API 상태, 호스트 규칙 또는 계수, 게스트 서비스 응답을 같은 시험 결과에 기록한다. 같은 호스트의 태그·untagged부터 확인하고 준비된 전용 환경에서 호스트 간 및 제공 범위의 IPv6·ICMP로 확대한다. 미실행 조합은 환경 조건과 함께 남긴다.

UI는 계정·도메인·프로젝트와 읽기 전용 역할을 검사한다. VM 메뉴의 공통 컴포넌트와 동작을 기준으로 소유자 선택, 작업 버튼, 오류와 재시도, 한국어와 라이트·다크 화면을 확인한다.

작업 브랜치는 `dhslove/epic-1996-security-groups`다. 검증을 마친 하위 작업을 구현 커밋으로 순서대로 추가한다.

## #1997 KVM 패키지와 설치본 검증

- 31번의 설치 RPM은 10월 13일, 32번은 10월 9일에 빌드됐다. 두 RPM의 실제 페이로드와 여섯 호스트의 스크립트 해시가 모두 일치했다. 기존 수정은 10월 29일에 병합됐다. [#1515](https://github.com/ablecloud-team/ablestack-cloud/pull/1515)
- CentOS 7·8 RPM 경로에서 소스 Git 리비전을 준비 트리에 기록하고 보안 그룹 스크립트의 SHA-256을 커밋과 준비 트리, RPM 설치 트리 사이에서 확인한다. 과거 스크립트를 준비 트리에 넣은 검증에서 RPM 빌드 전 거부됐다. 구현 커밋은 `64046566b22`다.
- 보안 그룹 파일 범위로 제작한 시험 RPM을 WSL의 격리된 RPM DB에 신규 설치하고, 양쪽의 기존 RPM 원본에서 각각 업그레이드했다. 세 경우 모두 소스의 SHA-256 `1fb96dcf70142069941c76961e7475b869f251f57b185b9ae80d006eadb2846f`와 일치했다.
- 다른 운영 스크립트의 개별 패치를 보존하기 위해 시험 호스트 `ablecube31-1`, `ablecube32-2`에는 시험 RPM에서 추출한 보안 그룹 스크립트와 해시 파일만 적용했다. Agent를 재시작하지 않았으며 기존 RPM 패키지 등록은 유지했다.
- 두 클러스터의 Mold UI에서 시험 물리망의 제공자를 활성화하고 VLAN 160·161 및 untagged Shared Network를 각각 만들었다. VLAN 시험 VM이 두 지정 호스트에서 Running에 도달했다. UI에서 추가한 TCP 18440와 UDP 18443 수신 규칙의 비동기 성공, Agent 적용 로그 및 각 VM의 설치 규칙을 확인했다. 지정 호스트의 비시험 IPv4·IPv6 FORWARD 목록은 전과 동일했다.
- `sg1996-qa-*` 시험망, 오퍼링, VM, 보안 그룹, 규칙은 리뷰용으로 유지한다. 연결 허용·차단 실측은 #1998에서 진행한다.

## #1998 Shared 보안 그룹 수신 격리

- 송신 정책에서 허용된 패킷도 목적지 보안 그룹의 수신 정책을 통과하도록 IPv4·IPv6 방화벽 경로를 수정했다. 기존 VM 체인의 송신 분기와 정책 규칙은 방화벽 테이블 단위로 교체한다. 연결 추적에 필요한 응답 흐름을 유지하고 적용 실패를 Agent에 반환한다.
- 구현 커밋은 3e10d34c15e다. 보안 그룹 파일 범위 시험 RPM을 빌드하고 ablecube31-1과 ablecube32-2에 스크립트를 반영했다. 두 호스트에서 IPv4·IPv6 규칙 구문 검사와 기존 정책의 재동기화를 확인했다.
- Mold UI에서 실제 보안 그룹 규칙을 추가하고 회수했다. 31번 VLAN 160·untagged, 32번 VLAN 161·untagged에서 같은 그룹, 같은 계정의 다른 그룹, 다른 계정의 새 연결을 비교했다. 빈 수신, 그룹 제한, 송신만 허용, 규칙 회수, CIDR 제한의 IPv4 TCP·UDP·ICMP 검사 240개가 모두 기대값과 일치했다. 허용 및 차단 카운터도 확인했다.
- 기존 VM 221대의 상태·배치 호스트·NIC·보안 그룹 연결과 시스템 VM 4대의 Running을 확인했다. 비시험 VM 4대는 기존 연결 경로의 ICMP 응답을 시험 전·중·후 확인했다. 이 중 3대의 SSH 포트는 시험 중·후에 새 TCP 연결로 응답했다.
- VLAN 162 Dual Stack 생성은 양쪽 UI의 IPv6 DNS 검증에서 멈췄다. 현재 시험 오퍼링에는 네트워크 DNS 입력란이 없고 두 존에도 IPv6 DNS가 구성돼 있지 않아 IPv6 실트래픽은 미실행이다. QA 브리지의 연결이 호스트별 dummy 인터페이스로만 구성돼 있어 호스트 간 트래픽도 미실행이다.
- 시험 VM 18대와 보안 그룹, IPv4 Shared Network 4개, 오퍼링을 검토용으로 유지한다.

## #1999 마지막 NIC와 브리지 규칙 정리

- VM 또는 NIC가 해제된 뒤 IPv4·IPv6 두 체인의 보안 그룹 포트 참조를 확인한다. 마지막 참조가 사라지면 Mold가 생성한 FORWARD 연결과 브리지 체인만 같은 테이블 작업으로 정리한다. 보안 그룹 포트가 남아 있거나 외부 규칙이 있는 경우 체인을 유지한다.
- 구현 커밋 deb5438ad3f의 보안 그룹 파일 범위 시험 RPM을 빌드했다. 31번 1·3번 호스트와 32번 2·3번 호스트에 스크립트를 반영하고 Agent 상태와 설치 해시를 확인했다.
- 두 클러스터에서 Mold UI 정지·시작 총 20회가 성공했다. 처음 정지한 VM의 참조만 사라졌으며 마지막 VM의 정지 후 시험 브리지 FORWARD 참조, 체인, 포트 규칙은 IPv4·IPv6 모두 0이었다. 재시작과 반복 정지 후에는 실행 중인 VM별 규칙 수가 일치했다.
- 31번 1↔3, 32번 2↔3으로 시험 VM을 UI에서 왕복 실시간 마이그레이션했다. 총 4회가 성공했고 각 복귀 후 3번 호스트의 시험 브리지 참조와 체인이 모두 0이었다.
- 네 지정 호스트의 비시험 IPv4·IPv6 FORWARD 목록은 변경 전과 일치했다. 기존 제어 VM 4대의 ICMP 응답과 기존 VM 3대의 새 SSH TCP 연결을 확인했다. 시험 VM과 네트워크는 유지했다.

## #2000 VM 소유 범위로 보안 그룹 변경

- VM 상세의 그룹 선택과 저장을 VM 소유 계정·도메인 또는 프로젝트에 연결했다. 기존 선택은 ID로 유지하며 권한과 지원 네트워크를 확인한다. 백엔드의 정지 상태 요건을 UI에서도 적용한다.
- 소유 범위나 VM이 바뀌면 이전 요청과 선택을 폐기한다. 저장 실패 시 선택과 창을 유지하며 성공하면 동일 VM을 갱신한다. 구현 커밋은 d4e99937f22와 990a178a19d다.
- WSL에서 소스맵을 제외한 UI 시험 모듈을 빌드해 31·32번의 활성 웹앱에 배포했다. 두 관리 서버의 WEB-INF와 /client/ HTTP 200을 배포 전후 확인했다. 이 단계의 최종 UI 번들은 app.11b97781.js다.
- 두 클러스터의 다른 계정 VM과 프로젝트 VM 각각에서 기존 default ID를 유지하면서 전용 그룹을 UI로 추가하고 서버에서 재조회했다. 일반 계정과 도메인 관리자 세션에서는 소유 계정의 목록과 저장된 ID를 확인했다. 읽기 전용 세션은 그룹을 읽을 수 있었고 변경 버튼을 볼 수 없었다. SG를 사용하지 않는 비교 VM에도 변경 버튼이 나오지 않았다.
- 브라우저에서 응답을 지연시켜 VM 전환 시 기존 창이 닫히는 것을 확인했다. 저장 오류 응답을 브라우저에서 모의했을 때 선택이 유지됐고, 이어진 실제 제출이 성공했다.
- 일반 계정 시험 VM을 원래 호스트에서 Running으로 복원했다. 프로젝트 VM과 소유 범위 확인용 그룹·역할은 유지했다.

## #2001 라우터 없는 Shared 오퍼링 생성과 복제

- UI 생성·복제와 요청 구성이 실제 선택된 VirtualRouter 또는 VpcVirtualRouter 제공자를 공통 기준으로 사용한다. 라우터를 사용하는 구성에서는 컴퓨트 오퍼링이 필수이며, 마지막 라우터 제공자를 제거하면 필드와 선택이 초기화된다. 구현 커밋은 79ed6415067이다.
- UI 시험 모듈을 빌드해 31·32번에 배포했다. WEB-INF와 /client/ HTTP 200을 유지했고 활성 UI 번들은 app.41e5151d.js다. 라우터 제공자 및 요청 매핑 검사 5개와 변경 파일의 린트를 통과했다.
- 각 클러스터의 SG 전용, SG+ConfigDrive 생성 및 SG+ConfigDrive 맞춤 복제가 UI에서 성공했다. 여섯 요청에 serviceofferingid가 포함되지 않았다. 각 서버는 라우터 없는 오퍼링 조회에도 시스템 기본 ID를 반환하므로 브라우저 요청과 저장된 서비스 구성을 함께 확인했다.
- 두 클러스터에서 VirtualRouter·VpcVirtualRouter의 컴퓨트 오퍼링 미선택은 UI에서 차단됐다. 유효한 선택 후 실제 요청과 저장값이 일치했다. 라우터 제공자를 제거했다가 다시 추가했을 때 기존 선택이 비워지는 것도 확인했다.
- 두 환경에 VLAN 162의 sg1996-qa-31-configdrive 및 sg1996-qa-32-configdrive Shared Network를 UI로 생성했다. 다음 ConfigDrive 실검증에서 사용할 망과 오퍼링을 유지한다.

## #2002 보안 그룹 규칙 입력과 방향별 권한

- 번호와 이름으로 SCTP(132)를 검색하고 선택한 번호를 보낸다. 선택한 프로토콜에 맞는 포트와 ICMP 항목을 표시하고, API 호출 전에 CIDR·그룹 참조·포트·코드를 검증한다. TCP 전체 포트 표현과 여러 CIDR을 유지한다.
- 수신·전송 규칙의 추가와 회수 권한을 각각 적용한다. 비동기 작업 동안 중복 제출을 막고, 실패하면 오류와 입력을 유지한다. 성공 후 해당 탭의 규칙을 갱신한다.

## #2005 SG+ConfigDrive 시작 진단과 ISO 유지

- 관리 서버의 ConfigDrive 위치 선택에서 보조 저장소 부재, 지원 형식, 용량 한도, SSVM 부재, Agent 응답 및 기록 실패를 구분한다. 오류에는 사용자 데이터와 Agent의 자유 형식 응답을 노출하지 않는다. KVM에서 명시적 호스트 캐시를 선택하면 주·보조 스토리지 없이 저장할 수 있으며, 주 풀 미지원에 대한 기존 전환 설정도 적용한다. ISO 기록 전에 CD-ROM 슬롯을 검사한다.
- 31번과 32번의 VLAN 162 Shared 보안 그룹 및 ConfigDrive 오퍼링을 사용했다. 최초 UI 시작에서 31번의 기존 오류를 재현했고 32번은 실행됐다. 31번의 NFS는 349.83GB 중 332.11GB를 사용해 90% 한도를 초과했다. 최종 빌드에서 동일 VM의 UI 오류에 용량 한도가 표시되고 VM과 NIC가 유지됐다. 이전에 성공한 캐시 ISO의 SHA-256도 실패 전후 같았다.
